# RE4 适配规范 (Games/RE4)

本目录是《生化危机 4 重制版》(REFramework 游戏名 `re4`,`chainsaw.*` 命名空间)的适配层,
补充仓库根目录 `AGENTS.md`。下面是长期有效的设计约束与实测结论,改动 RE4 代码前先读相关章节;
带「别重新提议」「踩过」的条目是讨论后的定论。

RE4 目前走**独立接入**:入口 `ArmorVariantManager.lua` 识别到 `re4` 后只调用 `Main.start`,
共享的 `App` / `Presets` / `UI` 不参与(REFF 只复用共享的注册桥 `UI/Reff/Bridge.lua`)。

**配置有两个版本**:v2(`base` + `axes`,规则挂在各层的状态上)和 v3(整套造型 + 平铺的状态组 +
条件状态表 + 预设库,见「v3 配置模型」)。v2 照常运行,由用户点「迁移旧配置」转成 v3,不自动迁移。

**界面分工**:ImGui(REF 原生菜单)是 legacy 界面,保留 RE4 用户原有的操作习惯,不向 MH 的界面靠拢;
v2 配置在 ImGui 里照旧完整可用,v3 配置在 ImGui 里只做日常使用和迁移(`ImGuiV3.lua`)。
新界面做在 REFF 上,按 RE4 的模型单独设计(`web/src/re4/`),只服务 v3。两边改配置一律走 `Ops.lua` / `OpsV3.lua`,
保证同一个操作在两个界面里语义一致;新增改配置的操作先加进 `Ops`,再让界面调用。原因是数据模型不同 —— RE4 的配置是 `base` 整套造型 +
`axes` 状态组的层模型(见「层模型」),而 MH 两款是 `groups`。旧 JSON 的路径、字段与行为语义按
兼容契约保留;以后要迁到共享界面,先证明 `Leon.json` / `Ada.json` 这类旧配置行为不变。

## 与原版的架构差异(移植前必须知道)

原版(`崛起版_v2.4.5` / `v3.3.0`)建在 MH 猎人护甲系统上:遍历 `ch##_###_###` 命名的部位子物体,
逐个找 `via.render.Mesh`,再逐材质 `setMaterialsEnable`。触发条件是 MH 专属的武器蓄力状态机
(大剑/盾斧/虫棍/弓/锤子……)。这套查找逻辑完全建立在 `app.*` 命名空间和 MH 的护甲部位切分习惯上。

实测 RE4(通过 reframework MCP,2026-08-22)确认:

- RE4 用 `chainsaw.*` 命名空间,`app.PlayerManager` / `app.Character` 之类的类型**不存在**。
- RE4 的可控角色**不是**靠遍历部位子物体拼出来的,而是直接在 `chainsaw.PlayerBodyUpdater`
  (所有玩家角色 BodyUpdater 的公共基类,`Ch0a0z0BodyUpdater`〔里昂〕等具体类继承它)上
  暴露了固定几个 `via.render.Mesh` 槛位:
  `get_BodyMesh()` / `get_HeadMesh()` / `get_HairMesh()` / `get_ArmorMesh()`(+`get_HasArmorMesh()`)。
  这比 MH 的护甲部位遍历简单得多——不需要按名字猜部位,直接四个槛位读到底。
- `chainsaw.CharacterContext` 上还有原生换装字段(`CostumeManager`/`CostumePresetID`/
  `requestCostumeChange()`),但本插件按约定**不use它**——原生换装走的是官方登记过的换装预设,
  给没有官方换装预设的自定义模型做条件触发式差分,还是走逐材质开关这条路更直接。
- **Ada(`ch3_a8z0`)已实测通过**,API 与里昂完全一致(2026-08-23):四个 mesh 槛位、
  `get_HitPoint`→`HitPointRatio`、`InSafeRoom`/`IsBattle`/`IsAiming` 全部可用,
  `HasArmorMesh` 同为 `false`。角色切换时插件能自动侦测到新的 `kind_id`。
  材质数不同(身体/头/头发 = 8/3/6,里昂是 16/2/4),配置按 `kind_id` 分文件所以不会串。
- **继承链深度会变,代码不能假定固定父类**:里昂是
  `Ch0a0z0BodyUpdater` → `PlayerBodyUpdater`,而 Ada 是
  `Ch3a8z0BodyUpdater` → `Ch6CommonBodyUpdater` → `PlayerBodyUpdater`(多一层,
  `Ch6Common` 看名字是 `ch6_*` 那批角色共用的基类)。
  我们用 `body_updater:call("get_BodyMesh")` 按方法名解析,会自动沿继承链往上找,所以不受影响 ——
  但**不要**写成"父类必须是 `PlayerBodyUpdater`"那种检查,那会把 Ada 判成不支持。
- 艾什莉可控段落尚未实测。`chainsaw.CharacterManager.PlayerKind` 里还登记了
  `PlA0`–`PlA7`、`Ch2_a1z0`、`Ch2_a3z0`,对应关系未逐一核对。

## 范围

- 已实测验证:**里昂(`ch0_a0z0`)、Ada(`ch3_a8z0`)** —— 同一套代码直接跑通,无需分支。
- 未实测:艾什莉可控段落。按同一基类推断应该能用,但要在对应段落跑一次
  `reframework_get_type` 确认继承链(注意链的深度会变,见上一节)。
- v0.1 只做 **HP 百分比**这一个条件。MH 版里「武器拔出/收起」用的是猎人武器收纳状态机,
  RE4 没有对应物——实测 `get_MeleeAttackType()` 只有 `Combat`/`CombatCombo`/`Invalid` 三值,
  是近战连击标记,不是持枪/收枪状态,**不能**当替代品用,所以这次先不做武器状态条件。
  MH 版里武器专属的蓄力状态机(大剑/盾斧/虫棍/弓/锤子)全部去掉——RE4 没有这套武器状态。

## 术语(别弄反,弄反过一次)

| 用户看到的 | 代码里 | 是什么 |
|---|---|---|
| **整套造型** | `config.base`(层) | 一整套外观;它的一份配置叫**预设** |
| **状态组** | `config.axes[name]`(层) | 一组**互斥**的状态,例如「条件切换-面部」 |
| **状态** | 状态组里的一个 `preset` | 组里的一档,例如 正常 / 低血量 / 受伤 |

同一个数据结构(层里的 `presets`)在两种层里有两个名字:整套造型里叫**预设**(它是一整套外观),
状态组里叫**状态**(它是某些部位的开关组合)。共用一个词会让人以为状态组里存的也是"一整套"。
实现见 `TP(key, is_base)`(同一 key 加 `_g` 后缀取另一份文案)。

**曾经把这两个词弄反过**(把组里的一档叫"状态组"、把组叫"条件状态"),
改文案时对着这张表核一遍。

v3 的用词(界面上的):

| 用户看到的 | 代码里(v3) | 是什么 |
|---|---|---|
| **整套造型** | `config.base` | 完整快照,同一时间生效一套 |
| **状态组** | `config.groups[i]` | 平铺;`scope` 显式列出它管的材质,组与组之间不重叠 |
| **选项** | `group.options[名]` | 组里的一档(v2 叫"状态") |
| **条件状态** | `config.conditions.states[i]` | 条件 + 要切换的整套造型 / 状态组选项;数组顺序就是优先级 |
| **条件切换** | `config.conditions.auto` | 总开关(v2 每层一个"自动") |
| **预设** | `presets/<id>.json` | 预设库里的一份完整 v3 配置,只是套用的来源 |

不用口语化的描述:是「被覆盖」,不是「被压过 / 被压着」。

## v3 配置模型(状态组平铺 + 条件状态 + 预设库)

为什么改:v2 的规则挂在每层自己的状态上,一个条件只能驱动一层,同一个条件要在几个组里各写一遍,
组与组之间也排不了优先级;存档、共用、认亲是按反馈陆续加的,不成体系。v3 借鉴 SKS 的键组和条件状态。

- **解算**只换"每层选哪个",叠加 / 溶解 / 护甲镜像仍是 `TransformManager` 里 v2 / v3 共用的 `make_build`。
  条件状态从上往下认领目标层,已被认领的层算"被覆盖";命中且独占时,下面的全部被覆盖;没被认领的层用手动选择。
  按血量驱动的条件状态每层组成一条链(规则同 v2);排在第一个血量状态之前的普通状态认领了这一层时,这一层不驱动。
- **作用域不重叠**(同 SKS 键组)。一个材质只属于一个组,所以组的叠加顺序不影响结果。
- **迁移等价**:每条 v2 规则变成只指向原处的条件状态,按"整套造型、状态组优先级、组内顺序"排列,全部不独占 ——
  每层的选择与 v2 一致。例外是 v2 作用域重叠的材质:分给优先级最高的组,迁移结果里列出来让用户检查。
  `tests/re4_model_v3.lua` 穷举条件组合核对等价性。迁移前写还原点。
- **引用按名字**:状态组、选项、整套造型都以名字为标识;改名必须走 `OpsV3`(同时改条件状态里的引用)。
  删除不清引用,显示为"引用失效",用户自己删。
- **预设库**:每个角色一份"当前配置"(唯一生效),预设只是套用的来源;套用是复制,先进自动保存(每角色 5 份)。
  匹配按指纹:预设整套造型快照的材质名 + 状态组作用域,逐槛位比对(完全 / 部分 / 不适用),当前模型上没有的槛位不算。
  **从不自动切换,只提醒**(定论:用户可能改了模型后另存了备用预设,自动切换会切错)。
  文件名用 ASCII 编号,显示名在文件里;json 接口删不了文件,删除写墓碑 `{deleted=true}`,新建时复用编号。
- **共用 / 独立 / 认亲取消**:同一角色的玩家、傀儡、雕像本来就共用一份配置(按角色识别);
  不同角色要一样就套用同一个预设。`find_kin` 只在识别不出角色时用来建第一份配置。
- **调色方案(子预设,2026-11-05)**:调色的底是「初始」= mdf2 原值,**只读**,不存在配置里(定论:用户不要可编辑的
  「常驻」层,那会让从原版新建的方案也显示「已改」)。`cfg.palettes[名]` 是调色方案;调色页里**选中就生效**
  (`cfg.palette_active`,存盘),调色页编辑的就是选中的那一份;选着初始时一改,自动新建「方案 N」并选中
  (`OpsV3.ensure_palette`)。方案另外可以被整套造型的预设(`base.palettes`)、状态组的选项(`groups[i].palettes`)、
  条件状态(`st.palette`)引用。叠加从下到上:初始 → 选中的方案(相当于手动选择)→ 整套造型的选择 → 状态组按叠加顺序 →
  条件状态(优先级低的先,高的盖在上面),按「参数 + 分量」合并(`Palette.merge`)。方案列表按新建先后排,没有排序操作。
  条件状态的调色**不独占**:命中的各自生效,只有独占状态能挡住排在它后面的;血量状态在血量进入区间(进度 > 0)时生效。
  写入时机:Main 每帧算生效的方案名单(`ModelV3.palette_layers`),名单变了就重写调色。
  **渐变(2026-11-06)**:名单变化时按来源定时长(`ModelV3.palette_sources` / `palette_fade_time`):进来的方案用带来它的
  条件状态的渐入(它自己引用的,或它认领的整套造型 / 状态组选项引用的),离开的用渐出,手动选择带来的用界面溶解时间
  (关掉 = 瞬间),取最长。`Palette.fade_begin` 记每个要动的参数**当前显示的值**为起点(中途再变就从屏幕上的值接着走),
  并先把它们记成 touched、记好原值;`fade_step` 每帧线性插值(映射里 enum / bool 的参数过半才切;
  **踩过**:混合模式要变的颜色层不能跨模式插值颜色 / 强度 —— 前半段还是旧模式,强度往上走会整片变色闪一下。
  映射里同一组的 `XXXParam.x`(混合模式)和 `XXXColor.w`(强度)配对(`discrete.couples`),模式要变时强度
  先降到 0、中点切模式和颜色、再升到目标,模式不变的层照常插值),走完再 `apply_mesh`
  写终点、还原不再覆盖的。首次、换实例、组合没变的重写(调色页里直接改值)是瞬间的;
  **踩过**:手动选方案 / 切整套造型提交时也带 force_reapply,不能拿它判断「瞬间」,否则手动切换全都没有渐变。步长同溶解(os.clock,每帧最多 0.1 秒)。
  还原到初始时优先用 mdf2 文件里的值(`Mdf2.file_value`,经 `Palette.apply_mesh` 的 original 回调),读不到
  (pak 里的原版材质、原生插件太旧)才用第一次写入前从网格读到的值 —— Reset Scripts 不还原材质,网格上可能留着上次写的值。
  旧配置里的 `cfg.palette`(常驻)在 normalize 时迁移成「常驻」方案并选中;已选了别的方案时补进选中的方案,外观不变。
  删除方案保留引用、显示失效;改名走 `OpsV3.rename_palette` 连带改引用。「替换 mdf」烘焙的是选中方案在这个槽位的值
  (烘焙后从方案里清掉,成为新的初始),选着初始时不给这个按钮。
  护甲同步身体外观打开时,护甲的调色照抄身体(`ModelV3.mirror_palette`,按材质名),调色页不列护甲材质;
  护甲自己调过的值留在配置里,关掉同步后恢复。方案存在配置里,预设库按整份配置保存,所以方案跟着预设走。
  独立面板(无 REFF)暂时只能在选中的方案上调(选着初始时同样自动新建)。
- **快捷键(2026-11-06,`Hotkeys.lua`)**:`cfg.hotkeys = { ["0".."9"] = 绑定 }`,Alt + 数字,只对主控角色 `player:*`。
  整套造型、状态组、调色**共用这十个键**;绑定可以是整个结构的**轮换**(按一下切到当前手动选择的下一项,到末尾回到开头;
  状态组含「（无）」、调色含「初始」)或**单项**。一个键一个设定、一个设定一个键(绑到别处就移过去)。
  用户定的:结构绑了轮换键后,它下面的项**不能单独绑键**,只有「参与轮换」开关(`skip` 列表);绑轮换时清掉同结构的单项键。
  改名跟着走,删除后失效的绑定清掉。旧的 `base.hotkeys`(只给整套造型的第一版)读入时迁移成单项。
  用户定的:**Alt + 数字**,按住 Alt 时屏蔽数字键换武器,不用 Ctrl(游戏里常用)。实测(探针挂了 share 和原生两层):
  换武器的数字键**只经过 `share.hid.Device.isDown(via.hid.KeyboardKey)`**,原生 `via.hid.KeyboardDevice` 对数字键
  从不返回按下,isTrigger / isRepeat 没人问数字键;按住 Alt 时把 isDown(数字) 改成 false 就不换武器。
  KeyboardKey 的数字值同 VK('1' = 49)。先 Alt 后数字才算快捷键,数字一直屏蔽到松开(中途松 Alt 也不漏);
  先数字后 Alt 照常换武器;没绑的数字不屏蔽;一个都没绑时 hook 什么都不做。条件状态接管整套造型时,
  左上角提示「条件接管中,结束后生效」。
- **一份配置是一个整体**:整套造型、状态组、条件状态一起套用,不做模块化组装(材质和模组绑定得比形态键紧)。
- **REFF 界面约定**:状态颜色绿 = 生效、红 = 被覆盖、灰 = 未命中,另有圆点形状区分;可折叠的栏默认收起
  (快速切换里的状态组块例外,默认展开);删改用文字按钮;拖动排序用浏览器原生拖放,不引入依赖。

## 打包

RE4 与 MH 两款共用仓库根目录的 `build_release.py` 通用包(见 `DEVELOPMENT.md`):

- **版本号只有一个**:入口 `ArmorVariantManager.lua` 的 `local version`,经 `ctx.version` 传给
  `Main.start`。RE4 代码里不要再写第二个版本号。
- `Games/RE4/**/*.lua` 自动进包;`tools/re4/` 下的调试脚本**不进包**。
- 荒野预览 DLL 在非 `MHWILDS` 游戏里加载后不做任何事;REFF 清单声明 RE4,页面在 `web/src/re4/`,
  覆盖 ImGui 面板的全部功能。面板里已经没有直接改配置的代码:改配置走 `Ops`,带文件 / 全局副作用的
  (独立、初始化、认亲、命名存档、还原点、定位)是 `Main.start` 里的共用函数,通过 deps 交给 `Reff.lua`。
- 用户数据仍在游戏的 `reframework/data/ArmorVariantManager/`,文件名与旧版一致,升级不用迁移。

## 条件系统

一条规则 = `{ conditions = {{type, op, value}, ...}, logic = "AND"|"OR", preset = 预设名 }`,
条件类型在 `Conditions/Registry.lua` 注册。**已实装 34 个**:
数值一个 —— `hp_ratio`;枚举一个 —— `hp_vital`(血量等级);布尔 31 个 ——

- **战斗**(17):`is_battle` `is_aiming` `is_wheel` `is_combating` `is_shooting`
  `is_pull_trigger` `is_shoot_dry_fire` `is_pump_action` `is_throwing` `is_reloading`
  `is_weapon_changing` `is_parry` `is_big_parry` `is_fatal_kick` `is_fatal_round_kick`
  `is_fatal_kill` `is_dodging`
- **姿态**(10):`is_crouch` `is_walk` `is_run` `is_quick_turn` `is_jumping`
  `is_falling` `is_landing` `is_ladder` `is_hook_shot` `is_boat`
- **受伤/状态**(4):`is_damaging` `is_upper_body_damage` `is_burning` `is_invincible`
- **血量变化**(2):`hp_decreased` `hp_increased`
- **模型槛位**(1):`has_armor_mesh`(护甲槛位是否已加载)

**其中一半是瞬时的**(开火、扣扳机、空枪击发、拉栓上膛、招架、处决系列、受击、
上半身受击、落地、快速转身、闪避、血量变化),单独用几乎看不见 ——
配「条件结束后保持」才好用。

这些布尔是用临时探测面板在里昂身上逐条实测挑出来的(2026-08-23 那一批,面板已移除,
见 `tools/re4/README.md`;`is_shoot_dry_fire` / `is_pump_action` 是 2026-08-25 用
`tools/re4/attic/GunProbe.lua.txt` 那个闩锁式探针补测的)。**文案按实测语义写、不按方法名直译** ——
理由见下面「实测出来的语义坑」。

`kind` 现在有三种:`bool` / `number` / `enum`。**`enum` 的档位列表由 def 自己给**
(`options(context, lang)` + `value_label(value, lang)`),Registry 不认识具体档位 ——
所以 `Condition_Vital` 是从引擎枚举的静态字段**反射**出档位的,这个游戏版本里真实存在的档
会自动全部出现在下拉框里,不用我们猜有几档、也不会把猜错的档写死在代码里。
反射失败才退回实测见过的 `Fine(0)` / `Danger(2)` 两档。

`enum` 的算子只有 `==` / `~=`:枚举值之间的大小没有意义(`Vital` 的 0/2/4 是标签,不是刻度),
给 `<` `>` 只会让人写出看着对、其实没定义的规则。

**整数只活在数据层,不进 UI**:引擎 API 返回的就是整数,名字是反射枚举静态字段反查来的 ——
所以"只按名字判定"做不到,代码里绕不开整数。但用户不需要看见它:下拉框显示名字
(`残血 (Danger)`),配置里存整数,规则列表也翻回名字显示。
想看原始整数就用 `HPDebug.lua`,那是诊断视角,显示成 `Danger (2)`。

`in_safe_room` **曾经实装、现已退出列表**(实测很难亮)。它的 id 是 v0.2 就发布的,
老配置里可能还引用着 —— **id 保留、不要拿去指别的东西**。引用它的旧规则会恒不命中
(`eval_condition` 找不到 def 就返回 false),在规则列表里显示成原始 id 字符串,
不崩、也不会误判成命中。

规则挂在**层**上(整套造型和每个状态组各有自己的 `rules`),命中时接管该层的选择。
多个同时命中时**状态列表里靠上的赢**(见下面「优先级」)。

### 跨版本兼容:读进来就升级,存回去就落地

配置**没有"新旧两种读法"** —— `load_config` 一律先过 `normalize_config`,在内存里就升级到当前
格式(`migrate_v1_to_v2` → `migrate_rules` → `reconcile_order` → `auto` 补默认值)。
之后任何一次改动触发的 `save_config` 写回去的就是新格式。所以:

- **不改就不写盘**:只是打开看看的话,盘上还是旧文件(升级只发生在内存里)。
- **改一下就整份升级**:哪怕只是拨一个开关,写回去的是完整的新格式,不会写出"半新半旧"的文件。
- **升级前会自动留一份**:`backup/<角色>.onload.json` 是本次载入时**原样**的内容,
  升级出问题可以从面板里一键回去。
- 迁移覆盖三类东西:**结构变化**(v1 的 `presets`/`groups` → v2 的 `base`/`axes`)、
  **字段补齐**(`order`、`auto`)、**条件 id 被删**(`hp_drop_elapsed` → `hp_decreased` + `hold`)。
  最后这类最容易漏 —— 它不是格式变了,而是引用的东西不存在了,漏了就表现为"配置突然不生效"。

**存档快照(`backup/*.slots.json`)不预先迁移**,它们是"当时的样子";被读回来的那一刻
照样走 normalize,所以升级在读的时候发生,而不是把还原点改掉。

### 「条件结束后保持 N 秒」:让瞬时条件真的看得见(v0.3.4 起)

规则上多了一个 `hold` 字段(秒)。**计时从"条件不再成立"那一刻开始** ——
条件持续成立期间一直亮、不倒计时;条件断掉之后再撑 N 秒。
(条件持续 5 秒、hold 2 秒 = 一共亮 7 秒,不是 2 秒。)
实现上是"条件成立的每一帧都把到期时间续到 `now + hold`",最后一次续期就发生在条件成立的最后一帧。

UI 在条件列表下面一行:`条件结束后保持(秒) [2] [应用]`,`0` = 不保持。
**曾经把这个标签写成「命中后保持」,那是错的** —— 它会被读成"从第一次命中开始算",
而实现从来不是那样。改标签别改回去。

**保持是整条规则的,不是每个条件各自的**:`eval_rule` 先把所有条件按且/或算完,
闩锁包在那个结果外面 —— 语义是「A 且 B,然后保持 N 秒」。
不做「A 保持 x 且 B 保持 y」:没有使用场景,而且两个闩锁重叠时说不清该谁赢。

**为什么它是规则的字段,而不是一个条件**(想做成条件的话,`掉血` 和 `保持中` 得组合起来 ——
这条一定会有人再提,所以把两种组合都试算清楚):

- 和「且」组合:瞬时条件(掉血)只在那一帧为真,`保持中` 要在那之后才为真,
  两者**永不同时成立** → 第一帧过后就灭了,保持根本没发生。
- 和「或」组合:第一帧命中 → 刷新计时 → 下一帧 `保持中` 为真 → 又命中 → 再刷新 →
  **永远不灭**(自锁)。

根因是 `保持中` 的真值取决于**这条规则自己命中过没有**,而规则是否命中又取决于它 ——
自我指涉。做成字段就干净了:**条件只回答"发生了吗",`hold` 只回答"亮多久"**。

它解决的是一整类问题:实测挑出来的那批条件里有一半是**几帧就过去**的
(开火中、扣扳机、招架、完美招架、处决系列、受击、投掷),差分闪一下根本看不见。
有了保持它们才真的可用 —— 这也是"把掉血和掉血后 N 秒拆开"的正解:
条件写 `上次掉血距今 <= 0.1`(近似瞬时),保持写 2 秒。

拍板的几个边角:

- **保持中算命中**,照常参与优先级竞争(受伤保持那两秒里压住低血量,正是想要的)。
- **计时状态不进配置**:用规则表当 key 的**弱表**(`__mode = "k"`),配置重载 / 换角色时
  那批 rule 表被丢掉,闩锁跟着被 GC 回收 —— 不会留下"上次没走完的计时",也不用手写清理。
  配置里只存 `hold = N`。
- **每帧会被调多次**(resolve、快速切换那一行、规则概览),重复续期是幂等的
  (都续到 `now + hold`),所以不需要像 `tick()` 那样保证每帧一次。
- 规则概览里也走带闩锁的判定 —— 否则"保持中"那两秒会显示成没命中,而画面上明明是它在生效,
  概览和实际打脸比不显示更糟。
- 时间源同 `hp_drop_elapsed`(`os.clock()` 墙上时间),游戏暂停照走;被高优先级压住时也照走
  (它记的是"事件多久以前发生的",跟谁在显示无关)。
- `hold` 只接受正数,`0` / 负数 / 垃圾值在 `migrate_rules` 里一律清成 `nil`。

**另一个语义(还没做)**:"最多亮 N 秒"(即使条件还成立也强制灭,用于"只想闪一下")。
它和「保持」是**两个不同的字段**,别用一个字段去兼容两种语义。等真有需求再加。

### 「自动」开关:暂时停掉一层的规则(v0.3.3 起)

每一层(整套造型 + 每个状态组)多了一个 `auto` 字段,快速切换里是个「自动」勾选框,
**只对有规则的层显示**(没规则时没有东西可自动,画出来是纯噪音)。

**语义是"规则跑不跑",不是"整层生不生效"**:关掉后规则整层不参与求值,回落到手动选的
那个状态。刻意不做成"整层失效",因为真实需求(拍照、试装、换模型)是**把脸固定成正常**,
而不是让这组消失;"彻底不管任何材质"本来就有入口 —— 把状态选成「(无)」。
于是两件事各管一件,不引入第三种语义:

| 想要 | 怎么做 |
|---|---|
| 规则接着自动切 | `[x] 自动` |
| 固定成某一个状态 | 取消自动,下拉选它 |
| 这层完全不管任何材质 | 取消自动,下拉选「(无)」 |

为什么需要它:在这之前,**有规则的层没有任何"先停一下"的入口** —— 想让面部差分别跟着
HP 和瞄准乱跳,唯一办法是去删规则,删了还得重建。而没有规则的层反倒一直有手动开关,
等于"被动层比手动层少一个能力",不合理。

三个实现细节:

- **`nil` 当 true**。老配置没这个字段,`normalize` 里写的是 `if layer.auto ~= false then
  layer.auto = true end` —— 只有显式 `false` 才是关,被写坏成别的类型也当开。
- **自动被关掉的层要在折叠区外面点名**(状态条下面一行「自动已停用: 条件切换-面部」)。
  关掉之后过两天很容易忘,然后以为规则坏了。
- **变化签名不用动**。签名只记"各层最终选了哪个状态",关掉自动后选的还是某个状态,
  签名照样正确反映,门控不受影响。

### 优先级 = 状态列表的顺序(v0.3.1 起)

**一个层里同时有多个状态的条件成立时,取列表里最上面那个。** 顺序用「上移/下移」调,
存在 `layer.order` 里。

真实的触发场景:HP 已经低于 30%(`低血量` 命中),这时又被打了一下
(`上次掉血距今 <= 1` → `受伤` 也命中)。这一秒该显示哪个?**看谁在上面。**
把 `受伤` 放在 `低血量` 上面 → 掉血那一秒显示受伤,1 秒过后自动回落到低血量。
规律:**越瞬时/越特殊的放越上面,常态放下面**。

之前是"遍历 `rules` 数组,**最后命中的赢**"。结果往往也对,但机制是隐形的 ——
数组顺序就是"当初谁先被添加",UI 里既看不见也改不了,把同一条规则删掉重加,
优先级就悄悄变了。**别改回去。**

为什么用状态列表顺序,而不是给每个状态填一个优先级数字:状态组本来就是一份**互斥**的
单选列表,它天然就是一份优先级表 —— 复用它就只有**一套**顺序,而数字会引入第二套
(列表按名字排、优先级按数字排,两者不一致时没人看得懂)。也考虑过"条件多的赢"
(类似 CSS 特异性),但上面那个例子里两边都只有 1 条条件,打平,解决不了问题,
而且"为什么它赢"无法预测。

配套的三件事:

- **`layer.order` 每次 `normalize` 都和 `presets` 对齐一遍**(`reconcile_order`):
  老配置没有 order(按名字排序补齐)、手改 json、以后哪个代码路径忘了维护 order,
  都在这里兜住。补进来的新名字排在**末尾**(优先级最低)—— 新建的状态突然压过所有
  已有状态会很意外。改名是**就地换名**,不是删了再补:后者会让改个名字就掉到末尾。
- **新建排末尾,复制插在源的紧后面**:副本是源的变体,优先级也该紧邻。
- **规则概览按优先级列,并且分「生效」和「命中,但被上面的压着」**:
  低优先级的规则条件成立时它确实命中了,只是没生效。两条都只标"命中"的话,
  用户会以为插件坏了(两个都说命中,画面只有一个)。目标状态已不存在的孤儿规则
  也照样列出来、可删除 —— 否则只能去改 json。

### 有状态条件与 `tick()`

`hp_decreased` / `hp_increased`(血量减少/增加)是**有状态**的条件 —— 它们是历史的函数,
不是当前值的函数。为此条件定义有个可选的 `tick(context, frame)`,由 `Registry.tick` 在
`on_frame` 里**每帧调一次**;`get()` 保持纯读。

**状态更新绝不能塞进 `get()`** —— `get()` 每帧会被调用多次(规则求值、状态栏、规则面板的
实时值显示),塞进去就会把"上一帧的血量"冲成"这一帧的",两个标志永远为假。

**多个 def 共享同一个 `tick` 时要靠帧号去重**:血量减少/增加是同一份血量历史的两个视角,
`Registry.tick` 会对每个 def 各调一次,第二次调用时基线已经被第一次更新过了,
算出来的差值恒为 0。所以 `Registry` 自己数帧、把帧号传给 `tick`,模块只在帧号变了时才采样。
**def 自己数帧是不行的** —— 那分不清"新的一帧"和"同一帧里的第二次调用"。

曾经有个 `hp_drop_elapsed`(上次掉血距今多少秒)。它把**事件**和**持续多久**揉在一个条件里:
`上次掉血距今 <= 3` 同时表达了"掉过血"和"3 秒内"。**有了「保持」之后这种写法就没必要了** ——
现在拆成 `hp_decreased`(血量减少,瞬时布尔)+ 规则上的保持时长。
`hp_increased`(血量增加)是白送的对偶,能做"回血时短暂变个表情"。

这两个布尔**只在变化的那一两帧为真**,所以基本上必须配保持。它们比"距今多少秒"更能推广:
开火、招架、处决、受击那十几个瞬时条件不可能每个都专门写一个有状态的 `*_elapsed` 模块。

`hp_drop_elapsed` 存档在 `tools/re4/attic/`。它唯一独有的能力是**反向表达**
(`> 10` = 已经 10 秒没被打了)—— 布尔说不出"很久没发生",真要用就把它捡回来。

**旧配置自动迁移**:`migrate_rules` 会把 `hp_drop_elapsed <= N` 改写成
`hp_decreased = 是` + `hold = N`(取和已有 hold 中较大的那个)。反向的 `> N` **故意不动** ——
它会在规则列表里显示成原始 id,看得见、删得掉,比悄悄改掉语义好。

时间源是 `os.clock()`(墙上时间),所以游戏暂停时计时**照走**。

### 变化签名只记决策,不记条件原始值(踩过)

`resolve()` 的 `changed` 签名一度包含所有条件的原始值。加入"距今多少秒"这类**持续变化**
的条件后,签名会每帧都变 → `changed` 恒为真 → 门控彻底失效。

正解:签名**只记各层最终选了哪个预设**。因为输出完全由此决定,条件只是喂给
`pick_active_preset` 的输入,原始值进签名本来就是冗余的。修了 churn,也更正确。

### 为什么两边都保留条件(讨论过要不要只放在状态组上)

考虑过把条件规则**只**允许挂在状态组上,让"条件"和"整套造型"形成干净的平行结构。
**否决了**,因为有一类需求只有整套造型的条件能便宜地表达:

- **章节换装**:`SituationType = ch1a_chap3` → 换另一整套
- **整套破损版**:HP 危险 → 几十个材质同时换成破损/血迹版

这类如果强迫用状态组表达,那个状态就得占住几乎全部材质 —— 等于退化成整套造型,只是绕了一圈。

所以判据是**这个条件想改的范围有多大**:

| 条件想改的范围 | 挂在哪 |
|---|---|
| 很多材质 / 就是想换整套 | 整套造型 + 条件 |
| 只有几个材质,其他维度要保持 | 状态组 |

整套造型的条件确实有"会顶掉其他维度"的坑(那正是状态组存在的理由),但那不是"该禁用",
而是"该说清什么时候用哪个" —— 已写进 `axes_hint` 的提示文案里。

**加新条件的成本**:布尔类往 `PlayerBools.lua` 的表加一行 + 补一条 `cond_<id>` 文案,
两步搞定;数值/枚举类照 `Condition_HP.lua` 写个模块再 register 一下。UI(下拉框、算子、
实时值显示)和状态签名都是从注册表自动生成的,不用改。

**规则语义演变**:v0.1 的 HP 阈值是"自动挑最贴合的一档、只生效一条";v0.2 起是通用条件
系统。v0.3 把规则收进层里,一层同时只有一个预设/状态生效。v0.3.1 起,多个同时命中时
**按状态列表顺序、靠上的赢**(之前是"rules 数组里靠后的赢",隐形且不可调)。
想做互斥的 HP 分档,把窄的放上面、宽的放下面,或者用 `>` 和 `<=` 夹出区间。
旧格式会在加载时自动升级(`migrate_rules` / `migrate_v1_to_v2` / `reconcile_order`),
用户不用手改。

`id` 是写进用户配置文件的 key,**发布后不要改**。

### 条件 backlog(实测确认可读,按需再开)

### 实测出来的语义坑(改文案前必读)

**方法名和实际语义经常不是一回事。** 这几条是在游戏里试出来的,不是从名字推的 ——
所以 `Localization.lua` 里的文案是按实测语义写的,别"修正"回字面意思:

| 方法 | 名字像什么 | 实测是什么 |
|---|---|---|
| `IsAiming` | 只要在瞄准 | **瞄准中还在动**才为真 —— **人物移动或视角移动都算**,站定不动就灭 |
| `IsWheel` | 船舵/转轮 | **站定瞄准/举刀**(含 space 举刀)。跟船没关系,`IsBoat` 才是船 |
| `IsHolding` | 举着武器 | **名副其实**,而且是 `IsAiming` ∪ `IsWheel` 的严格超集:两者亮的帧它全亮,另外补上起手/停步/放下的过渡帧;空格举刀也亮。已实装 = `is_holding`(2026-11-05) |
| `IsSprint` | 冲刺 | 正常跑步只亮 `IsRun`,没见 `IsSprint` 亮过 |
| `IsGround` | 站在地面 | 确实是站在地面 —— 但**几乎恒为真**,没有区分度 |
| `IsCombating` | 泛指交战 | 只有**近战攻击**(刀)才亮 |
| `IsShooting` | 开枪 | **真打出子弹**才亮(有弹药、射击成功) |
| `IsPullTrigger` | 扣扳机 | 只要按了射击键就亮,**空枪、没真打出也算** |
| `IsShootDryFire` | 空枪击发 | **就是空枪击发** —— 名副其实,别再用 `PullTrigger AND not Shooting` 去凑 |
| `IsPumpAction` | 泵动霰弹枪上膛 | 实测是**栓狙拉栓**(其他武器未测) |
| `IsDamaging` | 受到伤害 | **被普通攻击命中就算,零伤害也算**;但见下面那条 |
| `IsUpperBodyDamage` | 上半身被打 | 闪光弹也算(同时亮 `IsDamaging`) |

文案上的取舍:`IsShooting`/`IsPullTrigger`/`IsDamaging` 这几个,**语义差别写在这张表里
就够了,不往 UI 标签里塞括号注释** —— 「开火中」「扣扳机」「受击」比
「开火成功」「扣扳机(空枪也算)」「受伤中(命中即算)」好读,而且后者那种解释性标签
在下拉框里会被截断。`IsDamaging` 用「受击」不用「受伤」:它跟掉血不是一回事(零伤害也亮,
掉血也可能不亮)。

**最反直觉的一条:被控/特写类攻击掉血,`IsDamaging` 不亮** —— 被敌人擒抱束缚、
或者带特写动画的攻击,即使在扣血,`IsDamaging` / `IsHPChanged` / `IsInGrappleDamage` /
`IsJacked` 一个都没亮。所以"受击变差分"这类效果**不能只靠布尔条件**,
得配 `hp_drop_elapsed`(HP 掉了就亮,不管是怎么掉的)才盖得全。

`IsHPChanged` 和 `checkDyingMode()` 整个测试期间都没见亮 —— 前者猜是引擎内部的当帧标志、
到 Lua 这层已经被清掉了(**只是猜,没验**)。低血量要判断,用 `hp_ratio` 或
`getHitPointVital()`,那两个是实测有效的。

### `HPDebug.lua`:独立的改血工具

`tools/re4/HPDebug.lua` 是个**独立脚本**,和差分管理器没有任何依赖关系
(不 require 它的任何模块,单独删掉也不影响它)。面板上是一棵自己的树「HP 调试 (RE4)」。

它显示:当前 HP / 上限 HP / 百分比、当前**血量等级**(名字 + 原始整数)、以及
**引擎声明的全部档位**(`Fine=0 Caution=1 Danger=2 Dead=4` 这样一行)——
最后这条直接回答了"某一档到底存不存在",不用靠扫血去撞。
操作:`-10 / -1 / +1 / +10`、满血、只剩 1 点、归零(二次确认)、以及填数字写入。

三个刻意的设计:

- **不做滑条。** 拖动会每帧写一次 HP,一路扫过濒死/死亡阈值,把要观察的档位跳变自己冲掉。
  要扫阈值就一格一格走。
- **只用局部变量。** REFramework 的所有 autorun 脚本共享同一个 Lua 状态,写全局
  等于往别人家里放东西,重名了极难查。
- **归零要二次确认。** 它紧挨着其他按钮,误点的代价是直接死一次。

它的前身是「条件判断」面板底部的改血输入框(那个面板已移除,见 `tools/re4/README.md`)。
拆成独立脚本是因为**扫阈值这件事和差分管理器毫无关系** —— 它不该在一个换装插件的
面板里占位置,也不该随那个插件的移除一起消失。

### 时间维度条件(整类未做,需要先扩 Registry)

现在的条件全是"当前瞬时值",下面这类要给规则加状态机/时间轴才能做:

- **边缘检测**:进入/离开某状态的**瞬间**(而非"处于")。引擎帮了一半:
  `get_StateOld()` + `checkOldState()` 游戏自己就存了上一帧状态,
  `HitPoint.get_IsHPChanged()` 是引擎自带的变化标志。
- **增减/变化率**:HP 掉了多少、在多少帧内掉的 —— 能区分"缓慢流血"和"被一击重创"。
- ~~**闩锁/持续时间**~~ **已做**(v0.3.4 的 `hold`,见上面「命中后保持 N 秒」)。
  MH v3 原版是规则上的 `duration`,移植时砍掉过,现在以 `hold` 的形式回来了。
- **伤害事件详情**:`get_LastDamageInfo` / `get_DeadDamageInfo` / `get_LastNearmissInfo`(擦弹)
  各返回一份 `CharacterDamageInfo`,里面有伤害量、`IsKill`、命中**部位**+**左右**、
  `FromFront`/`FromBack`/`FromLeft`/`FromRight`(**来向**)、`WeaponID`、`AttackType`。
  → 可做"从背后被砍 → 后背破损差分"这种带方位的效果。属于事件类,要配闩锁才有意义。

### 事件回调(可替代轮询,未接)

这些是真 `Action` 委托,理论上能挂回调省掉每帧比对:`add_OnChangeBattleMode`、
`add_OnChangeCrouch`、`add_OnChangeSafeRoom`,以及 `CharacterContext` 上的
`OnChangeHitPointVital`、`OnChangeHitPoint`、`OnChangeCostume`、`OnChangedBodyGameObject`。

## 差分保持(v0.2)

差分被游戏冲掉有两种情形,`on_frame` 里各有一道检查:

1. **mesh 实例被换掉**(换装、模型重载、重生、场景切换)—— 之前写进去的材质开关必然全丢。
   每帧比一次四个槛位的 mesh 身份串(`Utils.get_mesh_identity`,四次指针比较),变了就无条件重刷。
2. **mesh 没换但开关被重置**(过场动画、动作结束时会发生)—— 每帧全量核对太浪费,
   隔 30 帧抽一次(`Utils.slot_state_drifted`),只核对预设里点名过的材质。

原计划是挂 `CharacterContext.OnChangedBodyGameObject`,改成自己比对,理由两条:
REFramework Lua 侧往托管 `Action` 字段追加回调不好办;更重要的是**「mesh 实例变了」这个
判据覆盖面更宽** —— 上面第 1 条列的四种原因都会让 mesh 换实例,而那个回调只在它自己
那几个时机触发。直接盯我们真正在意的不变量(我写过的那个 mesh 还是不是当前这个),
比盯"谁来通知我"更可靠。

顺带这也绕开了 Wilds 版 visibility controller 踩过的性能坑:那边是每帧递归遍历 Transform 树
找节点,这边四个槛位由 `PlayerBodyUpdater` 直给,加上状态签名门控,每帧的固定开销只有
四次指针比较。

## 层模型(v0.3)

只有**一种**「层」,两个变体,结构完全相同(`{ presets, active, rules, order, auto }`)。

**面板上的名字和代码里的名字故意不同** —— 代码/配置里叫 `base` / `axes`(不改,免得又要迁移),
UI 上叫**「整套造型」/「状态组」**。

命名演变过三轮:`主层`/`轴`(实现视角,用户看不懂)→ `整套造型`/`局部开关`
(命中了覆盖范围这个真实差别)→ `整套造型`/`状态组`(按主要用途命名:轴的价值几乎全在
**条件驱动**上,手动拨只是次要用途)→ 现在的 `整套造型`/**`状态组`**。

最后这一轮是为了**分清"组"和"组里的一档"**:`状态组` 这个名字没有为里面的每一档留位置,
于是里面那些(正常/低血量/受伤)一度被叫成"状态组",整个词对反了。
定成 `状态组`(组)+ `状态`(档)之后,两级各有名字,而且"一组互斥的状态"本身就说明了
组内单选这个事实 —— 见开头的术语表。

否决过的候选:`部件开关`(`部件` 和已占用的 `部位`〔body/head/hair〕太像,会混)。
同时把条件文案 `战斗状态` 改成 `战斗中` —— 那是**游戏**状态,得把"状态"这个词让给用户层,
否则状态栏里两种"状态"分不清。

| | 整套造型 `config.base` | 状态组 `config.axes[name]` |
|---|---|---|
| 预设内容 | **整份快照**(每个材质都有值) | **稀疏**(只含这个轴动过的材质) |
| 语义 | "一整套造型" | 一个可独立开关的维度 |
| 同时生效 | 一个 | 每个轴各一个 |

**「常规组 / 条件组」不是两类东西**,而是同一个层的两种**选择器**:`rules` 命中就用规则
指定的预设,否则用手动选的 `active`。所以条件规则不是独立概念,每一层都自带一份。

- **组内互斥自动成立** —— 一个层同时只有一个预设生效,这是定义决定的,不需要额外机制。
- **组间不冲突靠作用域** —— 轴的作用域 = 它所有预设提到过的材质的并集(`get_axis_scope`,
  自动推导,不让用户手工框选)。作用域不重叠时,叠加顺序不影响结果。重叠了会在 UI 里
  标出来(`find_scope_conflicts`),**不自动改任何东西,只报**。
- 每帧从基线整份重算,不依赖上一帧 —— 这同时也是"切换预设后残留上一个状态"的正解:
  不需要显式复位,因为基线本身就是重新铺的。
- 基线**总是先铺一层"全部材质启用"**,再盖整套造型预设。这样预设里没提到的材质
  (modder 后来新加的)才有确定值,而不是保留游戏当时的残留状态。
  选**(无)**时就停在全启用(引擎里没有原生分组可回退,见下面 viscon group 那条)。

### 护甲同步身体外观(v0.3.7,armor 是 body 完整重导出时用)

`config.armor_mirrors_body`,面板上是整套造型工作台顶部的一个勾选框,**默认开启**——
护甲和身体用同一套材质导出是常见做法,默认开比默认关更常对;真的是不同模型导出的
才需要手动关掉。开着的时候,
`TransformManager.resolve()` 在 base + 所有轴都合并完之后,**把 body 的最终结果整份
复制给 armor**(按材质名对应),armor 上任何单独配置(不管是 base 层还是某个轴写的)
全部作废。

这是给上一节那种"armor 是照着 body 完整重导出"的模型用的:与其让用户把 body 那份
配置在 armor 上再抄一遍(而且以后 body 每加一个状态组、每改一条规则,都要记得去 armor
上同步一次),不如让 armor **永远等于 body 算出来的结果**,配置量降到 0,以后也不用
惦记同步这件事。

**为什么是"完全覆盖",不是"body 填默认值、armor 自己配置的材质名可以盖回来"**:
两种做法讨论过,选了前者 —— 后者会出现"大部分镜像、少数几个手动"的半吊子状态,
排查"为什么这块没跟着变"会很麻烦;前者规则唯一:开着镜像,armor 就是 body 的镜子,
一个例外都没有,想要例外就先关掉镜像。

**只对"两边都有的材质名"生效**:armor 上如果有 body 没有的材质(实测里那些
model-specific 的额外材质),镜像不会去动它 —— 它就从这一帧的 resolved 结果里
完全消失,保持运行时原样,不强制成任何值。这和状态组"只管自己声明过的材质,
没声明的不管"是同一套逻辑,不另开一套语义。

**UI 侧**:镜像开着时,armor 从整套造型工作台和轴编辑器的「部位筛选」下拉框里消失
(继续显示是一堆点了没用的死控件),但**材质备注不受影响** —— 备注只是给材质起个
人看得懂的名字,跟镜不镜像无关,armor 的材质名照样值得备注。镜像开关**不按当前
armor 在不在显示**:皮肤切换会让 armor 随时冒出来,提前开好镜像、等它出现时直接
生效,比现开现关更顺手。

老配置没有 `armor_mirrors_body` 这个字段(或者被写坏成别的类型)一律当 `true`
(和 `layer.auto` 同一套写法:只有显式 `false` 才算关),`normalize_config` 里补的。

### `armor` 槛位其实跟皮肤绑定,不是战斗状态(v0.3.7)

**实测结论**(2026-08-24,用户反馈 + `MeshProbe.lua` 实测确认):`get_HasArmorMesh()`
**不是**"穿没穿护甲"这种游戏内动作,是跟**当前选的皮肤**绑定的 —— 里昂默认皮肤下
`armor` 槛位存在(24 个材质),切到别的皮肤就消失。之前代码注释里写着
"armor 在里昂身上恒为 false",那是**只测过默认皮肤以外的情况**得出的错误结论,已经改正。

**armor 出现时,通常会替掉部分 body 材质**:实测这具模型上 body 和 armor 两个槛位
各有 24 个材质,名字大量重叠(`BeltRibon` `Jacket` `Metal4` 这些两边都有)——
armor 是照着 body 的结构重新导出的一份完整槛位,armor 出现时对应的 body 材质在
视觉上是重复/穿模的。这类导出方式在护甲/换装类模型里很常见。

这件事对架构有两点影响,一点不需要动、一点需要新加:

**不需要动的**:mesh 实例切换的检测已经覆盖了皮肤切换。`Utils.get_mesh_identity`
每帧比对四个槛位的指针,armor 从"读不到"变成"有个新指针"会让身份串整体改变,
触发无条件重新应用 —— 这条路径本来就是为"mesh 被换掉"设计的,皮肤切换只是它的
一个具体案例,不用专门写代码去认皮肤切换这件事。§7 的匹配度修复也已经处理了
"armor 时有时无不该影响整套造型判定"。

**新加的**:`has_armor_mesh` 条件 —— 用户可以建一个状态组,专门在 armor 出现时把被
它盖住的那几个 body 材质关掉,这样材质冲突会**跟着皮肤自动联动**,不用每次换皮肤
都手动去关一次。**这件事插件没法自动做**:引擎不会告诉我们"这份 armor 具体盖住了
哪几个 body 材质",那是模型作者的私有知识,只有用户自己知道该关哪几个。

`has_armor_mesh` 走 `context:call("get_BodyUpdater")` 再取 `get_HasArmorMesh()`,
不是**当前帧的事实**,不需要 `tick()`。

### 材质匹配度只算"两边都有材质"的槛位(v0.3.7,armor 引发的)

`Utils.preset_match_ratio` 现在**跳过一边有、另一边没有的槛位**。这种槛位反映的是
**配置变了**(护甲穿上了、或者预设是在另一种配置下抓的),不是"这是另一个模型"。

起因:里昂的 `armor` 槽位**不是一直加载的** —— 穿上防护衣之后才出现,而且(待实测确认)
可能把 `body` 整个换掉。离线复现了这个场景,数字很清楚(身体 16 / 头 2 / 头发 4,护甲 10):

| 场景 | 改之前 | 改之后 |
|---|---|---|
| 没穿护甲(基线) | 1.000 可用 | 1.000 可用 |
| 护甲**追加**(body 还在) | 0.688 可用 | 1.000 可用 |
| 护甲**替换** body(body 读不到) | **0.188 → 判为不匹配** | 1.000 可用 |
| body 在但材质枚举为空 | **0.188 → 判为不匹配** | 1.000 可用 |
| 换成完全不同的模型 | 0.000 不匹配 | 0.000 不匹配 |
| modder 改了 2 个材质名 | 0.833 可用 | 0.833 可用 |

也就是说:**穿上防护衣的那一瞬间,用户所有整套造型都会被判「材质不匹配,已跳过」** ——
而那根本不是"预设不属于这个模型",纯属误判。改完之后穿脱护甲完全不影响判断。

**为什么不是简单写死"跳过 armor"**(最初的想法):那只解决"追加"的情形。如果护甲还替换掉
body,预设里那十几个身体材质会全变成只进并集不进交集,相似度 6/22 ≈ 0.27,**照样跌破阈值**。
一般规则(跳过单边槛位)把两种情形一起解决了。

**代价**:可比的槛位变少时,证据强度也变弱 —— 极端情况下只有头发能比,4 个材质名对上就
判可用。接受这个代价,因为另一头的错误更糟:误判成"不匹配"的后果是**用户配置整份不生效**,
而误判成"匹配"的后果只是套出一个不太对的样子、且用户一眼就能看见。
一个槛位都比不了时(空预设、或者预设记的槛位在这个模型上全不存在)返回 0,当不匹配处理。

### 预设与模型不匹配时怎么办

预设存的是材质**名字**。两种场景:

- **Modder** 频繁微调材质,少量增删改名 → 希望尽力匹配。
- **用户** 频繁换整个 mod,材质基本对不上 → 少数通用名(`Body` / `S_Hair` / `Metal1`
  这类到处都有)会**碰巧撞上**,于是"逐材质尽力匹配"会套出一个半残的样子。
  **这比什么都不做更糟**,而且这个场景比前者更重要。

所以不逐材质各自为政,而是**先整体判一次"这还是同一个模型吗"**:
`Utils.preset_match_ratio()` 算整套造型预设的材质键集与当前模型实际材质集的
**Jaccard 相似度**(交集/并集,键用 `槛位/材质名` 以免不同部位同名混算)。

| 场景 | 交集/并集 | 判定 |
|---|---|---|
| Modder 改了 2 个名字(20 → 22 个) | 18/22 ≈ 0.82 | 同一模型,尽力匹配 |
| 换了完全不同的 mod,3 个撞名 | 3/42 ≈ 0.07 | 不同模型,**整个跳过** |

用交集/并集而不是"交集占谁的比例",是因为它**两头都惩罚**(少了的和多出来的都算),
两种场景因此分得很开 —— 阈值 `MATCH_THRESHOLD = 0.5` 离两边都远,不敏感。

不匹配时**退回全启用**(= 模型作者原本的样子),并在预设列表里标 `[材质不匹配,已跳过]` ——
否则用户只会觉得"点了没反应"。

只对**整套造型**做这个判定:状态组是稀疏的,键集只是自己声明拥有的那一小撮,
推不出模型全貌;它引用的材质不存在时本来就会被忽略,天然降级。

### 为什么 v0.2 的 `groups` 是错的(别重新引入)

v0.2 加过一个"材质分组":每组自带预设库,按组名排序叠加,**没有作用域概念**。
它的本意是解决组合爆炸(N 个二元轴不必存 2^N 个预设),但**实现拿不到这个好处**:
那时候预设是整份快照,"兜帽"组的预设里存了全部材质的状态(包括夹克),叠加时会把
"夹克"组刚设好的值盖掉。**两个组不是独立的,是互相踩的**,轴一多结果就不可预测。

病根是**整份快照与独立叠加互斥**:一个层要能独立叠加,前提是它只对自己拥有的材质发言。
原版 MH 插件的 `mask` 正是干这个的 —— 它不是"精细可选",是承重墙。

同时也认识到,当初"切一次有效再切没反应"那个 bug,真正的病根不是稀疏,而是**没有作用域,
所以不知道该把哪些材质复位**;而"每帧从全启用基线重算"这一条就已经独立地治好了它。
整份快照是个钝的补丁:治了切换,弄坏了叠加。

v1 配置里的 `groups` 迁移时**原样搬进 `axes`**(不猜、不丢数据),它们的整份快照会被
作用域冲突检测报出来,由用户自己收拾。

### 中英文切换

面板最顶上一个 **「中文」** 勾选框,**默认不勾 = 英文**。选择存进
`ArmorVariantManager/GlobalSettings.json`(全局的,不跟角色配置走)。

两处实现要点:

- 勾选框放在**所有提前 return 之前** —— 否则"未找到角色"这类提示会卡在用户看不懂的
  语言里,而他又没有地方切。
- 标签固定写死 `中文`,不走 `T()`:英文界面下也得让中文用户认得出来。

文案全部走 `Localization.lua`,zh/en 两套 key 必须对齐(有校验)。
容易漏的是**动态拼出来的 key**:`slot_<槛位>`、`tri_<三态>`、`cond_<条件id>` ——
它们不会出现在"用到但未定义"的静态检查里,槛位标题和三态按钮就曾因为写死中文而漏掉。

### UI 组织

按使用频率倒序,高频在最上面:

0. **「中文」勾选框** —— 见上。
1. **状态条** —— 一行显示角色 / HP / 当前为真的布尔条件。
2. **快速切换** —— 常驻不折叠,**不出现材质/槛位字样**(这是给小白用户的入口)。
   给不给下拉框由**"这一层有没有条件规则"**推出,不额外引入"模式"标记:

   分成两块折叠区:**基础状态组**(没有条件规则)和**高级状态组**(条件驱动)。

   | 层 | 快速切换里的样子 |
   |---|---|
   | 整套造型 | **永远是下拉框**,即使挂了规则;有规则时旁边加「自动」勾选框 |
   | 基础组,**只有 1 个状态** | **勾选框**(它本来就是个开关) |
   | 基础组,**多个状态** | 下拉框(多档维度) |
   | 高级组(有规则) | 组名 + 「自动」勾选框;**自动开着时不给手动控件**,关掉才出现下拉框 |

   整套造型和状态组在这一点上刚好相反,别混:**规则对整套造型是例外**(比如只在某章节命中),
   所以它的手动下拉框必须永远在;**规则对状态组是主要驱动方式**,所以自动开着时
   不给手动控件 —— 规则永远压过手动值,那个控件点了没反应。

   两块各自**折叠**,摘要行列出自己那块当前生效的状态名 —— 每多一个组就在高频区多堆一行
   是不行的,而摘要让人不展开也能看清现状。**摘要只统计自己那块**:摘要行就是折叠标题,
   标题里提到的东西展开却看不见,读起来像坏了(试过"摘要含被动、列表只放可操作的",不成立)。
   哪一块空了就整块不出现。
   **不做"单选"**:状态组之间本来就是要能同时生效的,那是它们存在的理由。

   **这里推翻过一次自己**:早期刻意**不**按手动/被动分块,理由是"一给状态加规则,
   它就会从一个板块跳到另一个板块,位置乱跳更难理解"。加了「自动」开关之后这个判断变了:

   - 被动组从"不可操作"变成**可操作**了,再让它完全不出现就说不通(它有开关要露出来)
   - 但把它和基础组混成一列更难读:一个是"点一下就换",一个是"设好条件就别管了"
   - "位置会跳"仍然存在,只是用「基础/高级」这两个名字把它**解释掉**了:加了条件就升级成高级

   分块的判据仍然不是"模式标记",而是**这一层有没有条件规则**,由数据推出来 —— 没有引入
   任何需要用户维护的开关来决定它出现在哪一块。
3. **造型工作台(主层)** / **轴** —— 折叠,低频高投入。

### 条件挂在状态组上编辑,没有暂存区(v0.3.1,两轮反馈改出来的)

**最终形态**:选目标状态组 → 看见它现在的条件 → 加/删,改完立刻落盘。

```
▼ 条件规则(仅满足设定条件时,才启用)
  [2] 上次掉血距今(秒) <= 2 → 受伤      [删除]      <- 全层概览,顺序有意义
  [1] HP% <= 30 → 低血量 (命中)         [删除]
  ────────────────────────────────
  目标状态组(命中时切到)  [低血量 ▼]                <- 改哪一组
  ────────────────────────────────
  「低血量」在以下条件下生效:
    HP% <= 30                           [删除]
    且
    战斗中 = 是                          [删除]
  [添加新条件]                                       <- 点开才出表单
```

**改过两轮,别改回去**:

1. 第一版是「条件 → 算子 → 值 → 添加条件 → 条件组合 → 目标预设 → 添加规则」。
   反馈:顺序反直觉 —— 人想的是"我要在什么时候换成这一套",**目标是意图、条件是限定词**。
2. 第二版把目标提到最前,但还留着「本条规则的条件… → 添加规则」的暂存区。
   反馈:那一整块多余。心智模型是"这个状态组在什么时候生效",**不是**"我在构造一条规则";
   暂存区还多一个失败模式 —— 填完忘了点「添加规则」,什么都没发生。

所以现在:**没有暂存区,没有「添加规则」按钮**。条件直接加到选中的状态组上。
「添加新条件」表单默认收起(大部分时间用户是来看/删的),点开才出现;
表单里的「与已有条件的关系」**只在这一组已经有条件时才出现** —— 第一条条件没有可关联的对象。

**存储格式一点没变**(还是 `layer.rules` 数组,一条 rule = `{conditions, logic, preset}`),
所以不需要迁移。UI 只是把"编辑哪条 rule"绑到了当前选中的状态组:

- 加第一个条件时**才**创建那条 rule → 不会产生空规则
- 删掉最后一个条件时把整条 rule 一起删 → 空条件 rule 永远不命中,留着只会在概览里
  显示成一条什么都不做的幽灵
- 一个状态组理论上能有多条 rule(老配置、手改 json),编辑器只编第一条,
  其余的照样在概览里显示、可删除 —— **不藏东西**

**全层概览(上面那个列表)保留**,因为按状态编辑一次只看得见一个状态的条件,
看不出**全层的优先级关系**;它也是唯一能看出"多个同时命中时到底谁赢"的地方
(分「生效」和「命中,但被上面的压着」)。

**「且/或」的三处措辞**(踩过):
- 概览里的规则读作 `HP% <= 30 且 战斗中 → 低血量` —— 这里用 `logic_and`/`logic_or`(光秃秃的"且/或")
- 条件列表里显示在**行与行之间**,因为它是**整组共用一个**连接词,不是每对条件各有一个
- 表单里的选择器叫「与已有条件的关系」,选项写全「全部满足(且)」/「任一满足(或)」;
  它最早叫「条件组合」并且紧挨着「目标预设」,被读成了 **"且预设 / 或预设"**(真实反馈)

**讨论后没做:给规则目标加一个「(全局)」选项。** 提过,确认不需要 —— 别重新提议。

**「预设」这个词只属于整套造型层。状态组层里同一个东西一律叫「状态组」。**
数据结构完全一样,但用户心里是两回事 —— 一整套造型 vs 某个部位的开关组合;
共用一个词会让人以为状态组里存的也是"一整套"。改的是全部露出的地方:
新建状态组 / 当前状态组名 / 还没有状态组 / 用当前显示状态覆写这个状态组 / 目标状态组。

实现是 `TP(key, is_base)`:**同一个 key 加 `_g` 后缀**取另一份文案,不是到处写 if ——
漏改一处就会出现"新建状态组 / 还没有预设"这种半截子术语,那比统一叫预设更糟。
校验脚本会核对每个 `TP()` 用到的 key 都有 base 和 `_g` 两份、且没有没人要的 `_g` 孤儿。


### 讨论后保留:一个状态可以有多份预设(别简化掉)

提议过"一个状态组只保留一份预设(状态即预设)"。**部分采纳** —— 只改 UI,不动能力。

采纳的部分是对的:实际用到的状态大多是**二元开关**(`隐藏耳朵`/`隐藏右马尾` 这类),
对它们来说多预设是纯负担。所以单预设状态在快速切换里直接给**勾选框**,
新建状态时也自动带一份预设并选中,省掉一步。

**但不能真的去掉多预设能力**:多档维度(比如面部的 `正常`/`受伤`/`低血量` —— 同一批脸部
材质的三种样子)必须靠"状态内预设互斥"来保证确定性。若一个状态只能有一份预设,
就只能拆成三个状态,而它们全占同一批材质 → **正是使用者当时踩到的那个冲突**,
结果依赖状态名排序。

**「状态内预设互斥」就是多档维度的确定性来源** —— 这是这个能力的存在理由,不是冗余。

判据一句话:

| 想要的效果 | 怎么建 |
|---|---|
| 同一批材质的几种样子,只能选一种 | **一个状态,多份预设**(互斥) |
| 几件互不相干的事,想任意组合 | **多个状态,各一份预设**(独立勾选) |

`隐藏右马尾` / `隐藏左马尾` / `隐藏耳朵` 属于后者:三个独立状态,作用域互不重叠,
所以可以任意组合勾选。**这不是冗余** —— 3 个独立开关就是 3 个 bit,再怎么组织也需要
3 个独立容器。

也**不做"一个状态内允许多选"**:它能表达的东西和"多个独立状态"完全一样(纯分类,
与被否决的「造型组」同理),代价却是多一个"互斥/多选"模式标记,还要在状态内部再做
一次冲突检测。

三态按钮的循环顺序是 `—` → **关** → `开`,把「关」放在第一跳:状态最常见的用法是
隐藏部件,让最常用的目标一次点到而不是两次。

### 按身体部位选不同造型 = 一个整块纳入整个部位的状态组

不需要额外的架构层。建一个状态组,用编辑器里的 **`整块纳入(按当前显示状态)`** 把某个
部位(比如 `头发`)的全部材质一次纳入它的作用域,这个状态就成了"该部位独立选造型" ——
身体听整套造型、头发听这个状态,互不干扰。多个部位各建一个状态也行,
作用域冲突检测会保证它们不会互相抢材质。

这个能力本来就有(逐个把材质点成 `开`/`关` 即可),缺的只是批量入口:轴编辑器里
早就有 `全部释放(这个部位都不管)`,却一直没有反向的"整块纳入" —— 那是个不对称,已补上。

### 讨论后否决:整套造型之上再加「造型组」

提议过给整套造型加一层分组(把多个整套造型归类)。**否决**:

- 它是**纯分类,不增加任何表达能力** —— 整套造型本来就互斥,分组后还是互斥。
- 代价是实打实的:配置多一层、要迁移,而且**快速切换会变成两级下拉**(先选组再选造型),
  正好把留给小白用户的那条最简路径搞复杂了。
- 要分类,**命名约定零成本**:列表按名字排序,叫 `战斗-01`/`休闲-01` 自然就聚在一起。

重新考虑的触发条件:**单个角色的整套造型经常超过 ~20 个**。3–10 个时扁平列表 + 命名前缀够用。

### 做过又删掉的:溯源面板(别重新提议)

曾经加过一个"当前生效"面板,列出每个材质是被哪一层决定的。**已删,因为它没有信息量**:

- 作用域是**唯一归属**的,所以"谁决定的"按定义就没有歧义 —— 面板只能告诉你已经知道的事。
- 作用域万一重叠,已经有专门的冲突报告了,不需要靠溯源去发现。
- 想看最终结果,直接看游戏里的角色比读 20 行文字快得多。

教训:当时的判断是"有了作用域,溯源几乎免费"——这话没错,但**免费不等于有用**。
正是让归属变确定的那个设计,同时也把溯源的价值消掉了。

编辑器细节:

- **「浏览并编辑」是一个动作**,不是"调用"+"编辑"两个按钮:点预设名 = 选中它 = 立刻生效 =
  展开编辑区。拆成两个是错的 —— 编辑非生效预设时,改动会被 `resolve()` 按 `active` 那个
  预设重算后盖掉,屏幕上根本看不到自己在改什么(v0.3 早期真踩了这个)。
- **先建后改名,不是先取名后建**:`新建预设` 直接建、自动取名(`1`/`2`/`3`…)、立刻选中;
  名字之后在「当前预设名」框里改。"先在输入框取名才能创建"对用户是多一道门槛,
  常规工具都是先建后命名。`复制` 同理:后缀 `_1`/`_2`…,复制完直接切过去。
- 改名走 `rename_preset()`,**必须连带更新引用旧名字的规则**,否则规则会指向不存在的预设。
  改名**不做逐键生效** —— 那样每敲一个字都要挪一次表 + 存一次盘,中途还可能撞上已有名字;
  用「重命名」按钮显式提交。
- 剩下的复制/删除仍是独立控件。

### 命名存档是跨角色的(v0.3.7)

「预设存取」的列表列出**所有角色**的存档:自己的在前(显示存档名),别人的带前缀
(`ch3_a8z0 / 我的配置`)。读进来 = **复制成当前角色的配置**,来源那份不动。

**之前只能读自己的,那不是设计决定,是存储布局的副作用** —— 存档按 `backup/<角色>.slots.json`
分文件(和配置本身按 `kind_id` 分文件同一个原因),UI 就只列了当前角色那份。
存档本身是"一整份配置的快照",里面没有任何"我属于哪个角色"的绑定,所以跨着读没有任何障碍。

真正的限制在**材质名**上,而且它不是新问题:

- 两个角色用**同一个模型 mod** → 完全可用,这是最主要的用例
- 不同模型 → 相当于"把结构搬过来":状态组、状态、条件、规则、优先级、保持时长全都在,
  但整套造型会被判「材质不匹配,已跳过」,状态里引用不到的材质被忽略。
  把材质部分重抓一遍(「用当前外观覆写这个预设」)就能接着用。

三个刻意的选择:

- **保存永远写进自己那份文件**。不提供"存到别人名下",那只会让人搞不清谁是谁的。
- **只能删自己的**。在这个角色的面板上删掉另一个角色的存档太意外了。
- **换选择时撤销确认态**。读档是二次确认的,如果换了下拉框却保留确认态,
  那个「确认」按钮就会作用在新目标上 —— 点下去替换的是另一份东西。

枚举靠 `global_config.known`(已知角色登记表),不需要目录遍历 API;
每个角色的存档文件一个会话只读盘一次(读不到就缓存成空表)。

### 备份:两个还原点,都不挂在保存上

**先明确一件事:材质不匹配〔见上一节〕不会动数据。** 它是只读跳过 ——
`resolve()` 只决定"这个预设不往模型上套",配置文件里一个字都没改,换回原来的 mod
就又能用了。所以那条路径不需要备份。

真正需要兜的是两类事故,各配一个还原点:

| 还原点 | 文件 | 生成时机 | 管什么 |
|---|---|---|---|
| destructive | `backup/<角色>.json` | 删除预设 / 覆写预设**之前** | 唯一两个显式丢数据的操作 |
| onload | `backup/<角色>.onload.json` | 本次载入配置**时**(每角色每会话一次) | 渐进搞坏、**文件损坏** |

外加一层**二次确认**(防):点 `删除` 变成 `确认删除?` / `取消`。`删除` 紧挨着 `复制` 和
预设名按钮,误点概率最高,从源头掐掉比事后恢复有效。覆写、恢复备份同理。

**为什么需要 onload 这一份**:`load_config` 里 `json.load_file` 对**文件损坏**和
**文件不存在**都返回 `nil`,于是坏文件会被静默当成空配置;接着任何一次 `save_config`
(材质勾选是点一下就存盘)就把那个也许还能手工修的坏文件覆盖成空的了。
这条路径**没有任何显式的破坏性操作**,destructive 那一份救不了它。

onload 备份有一条关键守卫:**只有真从盘上读出东西才写**。文件损坏时 `raw` 是 `nil`,
这时若照写就会把上一次的好备份覆盖成空配置 —— 而那正是最需要备份的时刻。
存的是 `normalize` 之前的原样(连 v1 旧格式也照原样留着)。

**两份都不跟着 `save_config` 走**:日常编辑存盘极频繁,备份若跟着保存走会被立刻冲掉 ——
等发现删错时,备份里也已经是删掉之后的样子,等于没有备份。

**不做多档备份 / 备份浏览器**(讨论后否决):配置本身就是一个纯 JSON 文件,想留几份、
想用 git 管都行,比在 ImGui 里搭一套列表 + 时间戳 + 预览 + 部分恢复划算得多 ——
为一个罕见事件建一整套 UI 不值。

### ImGui ID 坑:`##` 和 `###` 不一样(踩过)

`##` 的 ID 是**整个字符串**的哈希(含前面的显示文字),`###` 才是只取后缀、把显示文字
完全排除在 ID 之外。

后果:部位标题写成 `身体 (body / 00) 16 材质 / 4 关##slot_base_body`,用户一取消勾选,
`4 关` 变 `5 关` → 整串变了 → **ID 变了 → ImGui 当成一个全新的树节点,默认关闭**,
表现为"点一下勾选框,栏目自己折叠了"。

**凡是显示文字会变的控件,一律用 `###`。** 本项目里这类有:部位折叠标题(计数会变)、
三态按钮(标签随 `—`/`开`/`关` 变)、预设名按钮(`●`/`○` 前缀随选中变)。
现在全文统一用 `###`,把"显示什么"和"是谁"彻底解耦。
- **部位筛选标签页** —— 实测里昂 `body` 有 16 个材质、`hair` 只有 4 个,做头发时不该
  滚过 16 行身体材质。折叠时仍显示摘要(`16 材质 / 3 关`),不展开也能看出哪里动过。
- **两套槛位命名都显示**(`身体 (body / 00)`)—— 代码里的槛位名来自引擎 getter,
  而 Blender / RE Mesh Editor 里看到的是 `00/10/20`,只显示一套就得靠脑内换算。
- **材质备注名**(`config.material_notes[slot][mat]`)—— `Metal1`–`Metal4` 这种名字对人类
  没有意义,靠试才知道是哪块。备注是**角色级**的,不属于任何预设(认清一次,所有预设和轴的
  编辑器里都跟着显示),没填就 fallback 到原始材质名,填了显示成 `腰带扣 (Metal3)`。
  **插件只提供机制和录入入口(「材质备注」面板),不预置任何名字** —— 名字由使用者自己填。
- **「定位」按钮**(材质备注面板内)—— 临时**只显示**这一个材质(同部位内其他材质暂时隐藏),
  3 秒后自动恢复。用来认清某个材质是哪块,省掉"改预设 → 看效果 → 再改回来"的往返。

  一开始提的方案是**闪烁**,当时被否决("连点勾选框就能看出来")。后来实际给二十多个材质
  起名时证明确实需要一个专门入口 —— 但改成了「只显示这一个」而不是闪烁:
  闪烁是"看哪块在动",小部件很容易注意不到;只显示这一个是"**还看得见的就是它**",没有歧义。

  实现要点:这个临时状态必须让每帧的应用逻辑**认它**,否则会被 `resolve()` 的输出或漂移
  检查覆盖回去。所以 `apply_resolved()` 多接一个 preview 参数盖在正常结果之上、预览期间
  **每帧重写**、并且**跳过漂移检查**(那时 mesh 状态是故意与 `resolved` 不一致的,不算漂移)。
  到时间自动清除并强制恢复一次,不留脏状态,也不写进任何预设。
- 整套造型的材质是**二值勾选框**;状态组的材质是**三态循环按钮**:
  `—`(这个状态不管它)→ `关` → `开`,只有开/关才进作用域。
- 勾选立刻同步到模型上(所见即所改);改成 `—` 时触发一次强制重算,退回基线值。
- `armor` 槛位在里昂身上 `HasArmorMesh = false`,自动不出现,不会有空标签页。

## 探索过但暂缓/排除的路线

- **双风格 UI(再加一套仿 MH「装备差分管理器」布局的皮肤)** —— 提过、写过计划、**废弃**。
  动机是降低跨游戏学习成本(用过 MH 那个插件的人能直接上手)。废弃原因:**原版作者打算
  改用 ref-d2d 重做界面**,所以 MH 的 ImGui 布局是个即将消失的移动目标 —— 照着它做,
  等于把学习成本对齐到一个马上就不存在的参照物上。
  (计划原文 `docs/dual-style-ui-plan.md` 已删。)

  留下三条仍然成立的结论,以后真要动 UI 架构时直接用:

  1. **任何多皮肤方案里,两套皮肤的能力必须完全相同。** 同一插件换皮肤后功能不一样,
     比 UI 丑得多 —— 用户会以为功能坏了,而实际是换皮肤换掉了。
  2. **动手前必须先把业务逻辑从绘制代码里抽出来**(一层 `Actions.*`)。现在绘制代码里
     混着 `snapshot_before_destructive` / `capture_current_as_preset` / `save_config` /
     `request_reapply`。复制 draw 函数改布局 = 逻辑跟着复制 = 两套必然漂移。
     判据很硬:皮肤文件里不该出现这四类调用。
     **这条独立于双风格仍然值得做**(纯卫生改进,任何 UI 改动都受益),只是不紧急。
  3. MH 布局里有三样是我们**故意没有**的,别在任何 UI 工作里顺手加回来:
     `排序`(要加 order 数组,是数据模型改动)、`设为默认`与`当前选中`分开
     (**会把已修的 bug 带回来** —— 编辑非生效预设时改动被 `resolve()` 盖掉)、
     分组按 `mask` 过滤材质(唯一值得要的,但该是两套皮肤共同的改进,不是某皮肤的特色)。

- **原生换装系统**(`CostumeManager`/`CostumePresetID`/`requestCostumeChange()`)——排除,不是因为
  技术上做不到(实测存在,`chainsaw.CostumeListGuiBehavior` 的换装菜单也证明它工作正常,
  甚至已有社区 mod 靠改一个 `_IsGrayout` 字段解锁全部选项),而是**语义不对**:它是在
  「多个已注册的服装资源」之间切,不是「同一个模型内部」切。对 modder 来说,把差分做成
  走这套系统,等于要把每个差分状态都注册成一套独立的服装资源——工作量跟直接做三套模型
  没有本质区别,违背了"模型内部低成本切换"的初衷,所以从一开始就没考虑用它。
- **viscon group / `via.render.Mesh:PartsEnable`**——这是引擎级别真实存在的原生分组机制
  (对应 RE Mesh Editor 里 `Group_x_Sub_y__zzz` 的 `x`,MHWilds 装备普遍烘了这份数据)。
  实测里昂的 BodyMesh/HairMesh:`getPartsEnableIndices()` 全部下标返回 `0`,
  `getPartsEnable()` 对明显可见的部位也返回 `False`——说明这套 API 在 RE4 角色模型上
  是**空的/未启用**(大概是 `PartsSelect` 这类开关没被这份资源打开),不是查不到,
  是 Capcom 的角色资源管线没往里烘数据。**暂缓**,等以后有自定义模型主动烘了这份数据再接。
- **比材质更细的"网格几何子块"级可见性**——运行时完全够不到:`getMesh()` 返回的
  `via.render.MeshResourceHolder` 在 SDK 类型库里是 0 字段 0 方法,顶点/索引缓冲、
  子网格划分这些压根没注册进托管反射系统。唯一路径是在建模阶段(Blender/RE Mesh Editor)
  把那块几何物理拆成独立材质槛位,拆完用现有的材质开关就能单独控制——不是运行时脚本能补的。

## 一个角色多个 KindID:借用 + 写时复制

同一个"视觉上的角色"可以有多个 `CharacterKindID`。实测:

| | KindID | BodyUpdater 链 |
|---|---|---|
| 剧情里昂 | `ch0_a0z0` | → `PlayerBodyUpdater` |
| 佣兵里昂 | `ch6_i0z0` | → `Ch6CommonBodyUpdater` → `PlayerBodyUpdater` |
| 剧情 Ada | `ch3_a8z0` | → `Ch6CommonBodyUpdater` → `PlayerBodyUpdater` |

配置按 kind_id 分文件,所以佣兵里昂默认拿不到剧情里昂的预设。

**规则:自动只发生在第一次,之后都是显式操作。**

1. **第一次遇到这个角色**(盘上没有它的配置文件)时,按材质指纹找同族 →
   找到就建立**共用**(`global_config.aliases`;`cfg_key()` 把两个 kind_id 解析到同一个键 ⇒
   同一份文件、同一份内存表,所以改动天然双向可见)。
2. 第一次且找不到同族 → **自动初始化**一个 `default` 整套预设(抓当前显示状态),
   让新角色一上来就有可用基线。
3. 之后想建立共用 → **「尝试匹配同族配置」**按钮(独立状态下可见)。
4. 想从共用中分出来 → **「创建独立预设」**(从当前共用内容拷一份,来源不动)。
5. 想重来 → **「初始化预设」**(先自动备份),只在**独立状态**下出现。

**代价(写在 UI 横幅上):共用期间的改动会同时影响来源角色。** 这是选共用换来的,
不能既共用又互不影响。

### CG 傀儡也是目标(v0.4.0)

过场动画里的角色**不是玩家那具模型**。引擎另外生成一批 GameObject
(`ch0a0z0_puppet` / `ch2a200_00_puppet` / `ch2a600_puppet` …),挂
`chainsaw.TimelineEventPuppetChara`。它们**没有 `CharacterContext`,也没有 `BodyUpdater`** ——
mesh 直接躺在组件字段上。v0.3.x 的主循环从 `getPlayerContextRef()` 起步、拿不到
BodyUpdater 就 return,所以**一进 CG 差分全没了**。

实测(RE4 1.x,CG `EventID=50400`):

| GameObject | `get_CharacterKindID()` | 解析为 | 四个槛位 |
|---|---|---|---|
| `ch0a0z0_puppet` | 100000 | `ch0_a0z0` | body/head/hair + 子物体 `body_armor`(cha001_00) |
| `ch2a200_00_puppet` | 200031 | **`ch2_a200`** | body/head/hair,无 armor |
| `ch2a600_puppet` | 200034 | `ch2_a600` | body/head/hair,无 armor |

两条要点:

1. **傀儡自带的 kind 不一定是你心里那个角色的 kind。** 里昂傀儡正好是 `ch0_a0z0`
   可以直接用;Ada 的 CG 傀儡却是 `ch2_a200`(剧情 NPC 的 kind),不是可操作 Ada 的
   `ch3_a8z0`。**这里不做硬编码映射** —— 照旧按自带 kind 登记,交给既有的材质指纹
   认亲(`find_kin`)建别名。硬编码表要逐个角色维护,而认亲机制本来就是为
   "同一个人的多个 kind"造的。认错了在面板上用「创建独立预设」改。
2. **armor 槛位在组件上没有字段。** `_BodyMesh` / `_HeadMesh` / `_HairMesh` 有,
   护甲只以第四个子物体的形式存在。**别按子物体名字认槛位** —— 名字根本不统一:
   里昂傀儡是 `body` / `head` / `hair` / `body_armor`,Ada 傀儡却是
   `cha200_00` / `cha200_10` / `cha200_20`(直接拿 mesh 文件名当名字)。
   做法是拿那三个字段的**指针**去比对子物体上的 `via.render.Mesh`,剩下那个当 armor。

落地方式是新增 `Targets.lua`,把"一具能写材质开关的模型"抽象成目标;
`Utils.get_mesh(source, slot)` 同时认 BodyUpdater(userdata)和 `{[slot]=mesh}` 表
(靠 `type()` 区分),所以 `TransformManager` 和整个 UI 一行都没改语义。

**条件求值复用本地玩家的 context。** 傀儡没有自己的 context,而 CG 里 HP 之类的数值
仍然是"你现在这个角色"的数值 —— 这样既有条件一条都不用改。

**`Registry.tick()` 必须留在目标循环外面。** 放进循环的话,场上有几个目标它就 tick 几次,
"上次掉血距今多久"这类量会按目标数成倍走快。

**面板要能选中傀儡,不能只在后台默默应用。** 傀儡按自带 kind 登记、首次出现时会自动
认亲;认错了得有地方改,而「独立/共用」那两个按钮操作的永远是"面板当前显示的这个角色"。
选不中傀儡,它认错的别名就永远改不回来。

#### 两个踩过的引擎坑

* `findComponents(System.Type)` 返回的是 **SystemArray,必须先 `get_elements()`**
  转成 Lua 表。直接 `ipairs` 一个 SystemArray 会跳过第 0 个元素、还会越界读一格
  (REFramework 文档明写),表现就是"场上第一具傀儡永远不生效"。
* `sdk.typeof(name)` 给的是 `System.Type` 实例(`getComponent` / `findComponents` 要的就是它),
  和 `sdk.find_type_definition` 给的 `RETypeDefinition` **不是一个东西**,别混用。

`findComponents` 要扫全场景,**不能每帧跑**。傀儡的生灭以过场事件为单位(秒级),
所以隔 60 帧重扫一次、中间沿用缓存。重扫结果**按名字排序**:`findComponents` 的返回
顺序不保证,而面板的目标下拉是按下标选的,顺序一变用户选中的目标就会自己跳。

### 模型鉴赏的雕像:只借用,不登记(v0.4.0)

第三种目标形状,和玩家、CG 傀儡都不一样:

```
FigureWindow_RootObject → …_OperationRoot → …_RootOperationMove → …_RootOperationRotate
  └ FigureModel_Figure00_010     chainsaw.FigureModelController   (init(chainsaw.FigureId))
    └ Figure00_010_Body          Transform + Motion + DummySkeleton,自己没有 mesh
      ├ Body    cha002_00  24 材质
      ├ Hair    cha000_20  12 材质
      ├ Head    cha000_10  10 材质
      ├ Jacket  cha002_01   2 材质   (Jacket_Mat / JacketFur_Mat)
      └ Figure02_010_Body  wp4000_00  ← 武器道具,不是身体部件
```

**雕像没有 CharacterKindID。** `FigureModelController` 只知道一个 `chainsaw.FigureId`
(184 个值,`Figure00_000`…`Figure32_020`),`FigureModelSetting` 里只有镜头/布料/姿态参数
加一个 `FigureCategory`。所以傀儡那套"按自带 kind 登记 + 认亲"在这里没有东西可挂。

而且角色归属**推不出来**:`Figure00_010/020/030` 是里昂,`Figure00_080` 却是 Ada,
`Figure20_020/030` 也是 Ada —— 不是前缀规律。

**归属策略:只借用。** 按材质指纹在已知角色里找最像的一个,直接套它的配置 ——
**不进 `known`、不建 alias、不自动抓 default、不写盘**。
理由:雕像是"里昂的**像**",不是"一个里昂";想要的是"把里昂的差分套到雕像上",
不是"给雕像单独配一套"。也顺带避免 184 个 FigureId 把角色列表撑爆。

匹配动作收在 `Targets.set_borrow_resolver()` 这**一个注入点**里
(实现是主脚本的 `find_borrowable_kind`),识别机制以后要换的话只动这一处。

实测 `Figure00_010` 对 `ch3_a8z0` 配置的 Jaccard ≈ **0.87**
(body 24/24 + hair 12/12 + head 5/11),稳过 `KINSHIP_THRESHOLD`。

#### 槛位靠子物体名字 —— 和傀儡刻意相反

傀儡的子物体名不统一(`body` / `cha200_00` 混着),只能靠指针比对;
雕像这边名字固定(`Body` / `Head` / `Hair` / `Jacket`),而且**必须**用名字白名单:
子物体里混着武器道具(`Figure02_010_Body` → `wp4000_00`),
傀儡那套"取剩下那个 Mesh 当 armor"在这里会**把枪当成护甲**。

#### `Jacket` 刻意不收(踩过)

最早把 `Jacket`(cha002_01)映射成 `armor` —— 理由是"和傀儡的 `body_armor` 一致,
而且 armor 镜像 body 时那两个材质名对不上,会自然被忽略"。**这个理由只想到了应用路径,
没想到匹配路径。** 结果 `Figure00_010` 死活匹配不上,而其它五个雕像都正常。

实测(对着盘上真实配置算):

| Jacket 归属 | 最高 Jaccard | 匹配到 | 结果 |
|---|---|---|---|
| → `armor` | **0.581** | — | 低于 `KINSHIP_THRESHOLD`(0.6),整个雕像不受管 |
| 不收 | **0.896** | `ch0_a0z0` | 正确(Figure00_010 是里昂) |

原因:本插件的 `armor` 指的是"**把 body 的材质名整套重导出**的护甲 mesh"
(`armor_mirrors_body` 整个机制就建立在这上面),存下来的 armor 材质集是
`Band` / `BeltRibon` / `Body` / `Cable` … 这 23 个身体名;而 `Jacket` 只有
`Jacket_Mat` / `JacketFur_Mat` 两个毫不相干的名字。
于是 `preset_match_ratio` 在 armor 这一槛上拿到**两边都非空、却完全不相交**的集合 ——
那条"一边空就整槛跳过"的保护**不会触发**,交集 0、并集 +25,纯扣分。

而且收了它**什么都换不了**:armor 镜像 body 时写下去的是 body 的材质名,
那两个名字在 jacket mesh 上根本不存在,`apply_preset_to_slot` 一个都写不进去。
零收益 + 砸掉匹配 ⇒ 不收。

`Figure00_010` 是 costume 02,六个雕像里**只有它**有独立的 `Jacket` mesh,
所以只有它中招 —— 这种"只差在一个子物体上"的不对称最容易看成偶发。

真想管雕像的外套,得老老实实加**第五个槛位**,不能挤在 `armor` 上。

#### 匹配失败不能永久缓存(同一类时序坑)

匹配上了就缓存整个会话(读全部 json 很贵),但**失败只重试有限几次**。
雕像刚加载时 mesh 在、材质却可能还没就绪(`get_MaterialNum` 返回 0),
这时算出来必然 0 分;一次就钉死成"不受管"的话,
"Reset Scripts 那一刻正显示着的那个雕像"会永远匹配不上,之后翻到的都正常。
只差在时序上的毛病最难查。

只实测过 `Figure00_010`。别的雕像若用了别的子物体名,这里解不出槛位 ⇒
**那个雕像不产生目标(静默跳过)**,不会误套到别的部位上。

#### 同一个 mesh 路径,材质集可以不一样(反直觉)

雕像的 `Head` 是 `cha000_10`,**10 个材质**
(Face / Face_Reload / Face_Angry / Face_Cry / Face_Fear / Face_Shocked / Face_Aim /
Face_Hit / Face_Dead / Face_LowHP);
而 `ch0a0z0_puppet` 的 `_HeadMesh` 是**同一个路径**,却只有 **6 个**
(Iris / Face / Face_Aim / Face_Hit / Face_Dead / Face_LowHP)。

材质来自 mdf2,不是 mesh —— 所以"同一个 mesh 文件 ⇒ 同一套材质"是**错的**。
head 那一槛的匹配度单独看只有 0.45,全靠 body / hair 拉起来。

#### 雕像不进目标下拉框(这是保护,不是省事)

面板里有三处按钮是"从当前模型抓一份快照":「初始化预设」、编辑器的「用当前外观覆写」、
新建整套造型。选中雕像时它们会去抓**雕像的**材质集、写进被借用角色的配置里 ——
而上面那条正说明两者并不一致,抓完就把角色配置污染了。

让雕像**选不中**,这三条路一次全断,比在三个地方各加一个 `if` 更可靠。
代价:雕像上用不了「定位」预览。面板改为只读列一行 `[借用配置] <雕像名> -> <kind>`,
让"匹配到了谁"看得见。

#### 借用匹配为什么没和 `find_kin` 合并

三点不同:(1) 没有"自己"要排除,雕像压根不在 `known` 里;
(2) 走 `cfg_key(other)` 解析别名后再读文件 —— 共用中的 kind 自己那份文件是被旁路掉的,
读原名会拿到 nil,不解析的话这些角色永远匹配不上;(3) 结果只读,不写 alias / known。

指纹匹配要把每个已知角色的 json 都读一遍,很贵,所以**按雕像名缓存整个会话**
(缓存 `false` 表示"匹配过、没找到")。代价:配置改动后缓存会过期到下次 Reset Scripts。

### 做过又推翻的:"只要配置为空就自动处理"

曾经把触发条件设成"配置**实质为空**"(而不是"文件不存在"),并配一条"初始化必须产出非空"
的不变量来防死循环。**两条都推翻了**,因为它们合起来产生两个更糟的问题:

1. **「找同族」那条分支实际不可达** —— 两条分支同一个触发条件,而自动初始化总会成功,
   所以只要它排在后面就永远轮不到匹配失败之后…… 反过来排前面也一样:一旦自动初始化
   写过东西,配置就不再为空,匹配再也不会被触发。
2. **`default` 永远删不掉** —— 用户删掉最后一个预设,下一帧立刻被重建。

期间还踩过一个独立的 bug:检查只写在载入路径上,而 `loaded_configs` 缓存了配置表,
所以运行时删空**根本不会重新检查**。当时的修法是抽出 `ensure_config_not_empty()` 每帧调用 ——
那个修法是对的(不变量要持续维持,不能只在入口查一次),但**不变量本身才是问题**。

正解是**把匹配改成显式按钮**:循环从根上不存在了,于是"配置永不为空"这个不变量也不需要,
`default` 又能删了。自动行为只保留在"第一次遇到"这一个确定的时刻。

### 试过但更差 / 走不通的

- **写时复制**(先借用,一改动就自动分家):**默认值放反了**。对"同一个里昂的两个 object"
  来说,一改动就分家等于**把一个里昂当成两个** —— 而这正是最常见的场景。
  反过来"里昂和 Ada 用了同一个 mod"这种要分开的情形,用户一眼就知道,点一下独立即可。
  默认值该照着常见情形放。
- **在认出同族时弹「共用还是复制」二选一**:多一次打断,而两个出口做成事后按钮就够了。
- **`CharacterManager.calcPlayerKind(kindID)`** —— 本以为能拿到权威的角色身份,实测
  剧情里昂、佣兵里昂、剧情 Ada **三个全都返回 `PlA0`**。它是"玩家槽位"不是角色身份。
- **靠 `Ch6CommonBodyUpdater` 判断"这是佣兵模式"** —— 不成立,剧情 Ada 也走这个基类。

### 两个阈值:数值接近但别合并

| 常数 | 值 | 问的问题 | 分母 |
|---|---|---|---|
| `SLOT_MATCH_THRESHOLD` | 0.25 | **这个槛位上**这份预设还能用吗 | 单个槛位 |
| `KINSHIP_THRESHOLD` | 0.6 | 这俩 kind_id 是不是同一个角色 | 跨槛位聚合 |

(原来那个聚合的 `MATCH_THRESHOLD = 0.5` 已经没有了,见下面「逐槛位闸门」。
两个常数**分母不同,数值不可比** —— 别看着一个 0.25 一个 0.6 就想统一。)

`KINSHIP_THRESHOLD` 一开始按"必须完全一致"取了 **0.95,是错的** —— 那建立在
"能看到对方当前的材质集"这个假设上,而实际**只能通过对方存下来的预设去看**,
那些预设会随 mod 更新变旧。结果是永远匹配不上。

实测(里昂剧情 vs 佣兵,同一个 mod,对方配置略旧):

| 对比 | Jaccard |
|---|---|
| `ch0_a0z0` 的三个预设 | **0.750 / 0.750 / 0.722** |
| `ch3_a8z0`(Ada,真的不同角色) | **0.000** |

分离度极大,所以 0.6 两头都有大余量。两个常数数值接近但**别合并**:问的问题不同,
将来可能各自调整。

### 配置键改成角色名:角色识别为主,指纹为辅(v0.4.0)

`kind_id` 是"角色槽位"不是"人":`ch0_a0z0`(剧情里昂)和 `ch6_i0z0`(佣兵里昂)是同一个人,
`ch2_a200`(本体 NPC Ada)和 `ch3_a8z0`(DLC 主控 Ada)也是。而模型鉴赏的雕像**根本没有 kind**。
原来靠材质指纹补这一层,但实测这套 mod 下**跨角色材质名 Jaccard = 1.000**
(一个模型替换给了多个角色)—— 指纹在角色之间是精确的零分辨力。

现在身份由 **head mesh 编号**决定(见 `CharacterId.lua`),配置键就是角色名。

#### 解析顺序

| # | 条件 | 键 |
|---|---|---|
| 1 | `<角色名>.json` 存在 | 角色名 |
| 2 | `cfg_key(kind_id).json` 存在 | 角色名(顺带迁移) |
| 3 | 角色已识别、两者都没有 | 角色名(玩家/傀儡新建用);雕像 → 不受管 |
| 4 | 角色识别不出来 | `cfg_key(kind_id)`,并允许指纹认亲 |

#### 第 3 条为什么不回退指纹

**弱信号不能覆盖强信号。** 已经确定这是 Leon 了,再让指纹去找配置只会找到别人的
(材质名 1.000,必然误中),那比"暂时不受管"更糟 —— 后者至少不会把 Ada 的差分套到
Leon 身上。所以 `load_config` 多了个 `allow_kin` 参数,**只有第 4 条(身份未知)才传 true**。

顺带一个好处:认出角色之后**根本不用跑指纹**,而指纹要把每个已知角色的 json 都读一遍。

#### 迁移:显式正身,不猜,不删

多个旧 kind 键映射到同一个角色、内容又不同时,用哪一份是**领域知识,引擎不告诉我们**。
`CharacterId.PRIMARY_KIND` 显式写下来:`Ada = "ch3_a8z0"`(DLC 主控是正身,
`ch2_a200` 是剧情 NPC,后者那份 head 槛位只有 6 材质 —— 是在傀儡身上抓的快照)。
没有歧义的角色(Leon / Wesker…)不需要填,用目标自己的旧键即可。

**迁移只新建、不动旧文件。** 出错的话删掉新文件就回到原状,不需要恢复备份。

对着实际盘上状态模拟过,正序/反序结果一致:

```
player Leon    kind=ch0_a0z0  head=cha000 -> Leon    (migrated)
player Ada     kind=ch3_a8z0  head=cha800 -> Ada     (migrated)
puppet NPC-Ada kind=ch2_a200  head=cha200 -> Ada     (character)   ← 自动共用
puppet Wesker  kind=ch2_a600  head=chj000 -> Wesker  (migrated)
merc Leon      kind=ch6_i0z0  head=cha500 -> Leon    (character)   ← 自动共用
figure Fig00_010  (无 kind)   head=cha000 -> Leon
figure Fig10_010  (无 kind)   head=cha000 -> Leon    ← 原来指纹 0.292 直接拒掉
unknown ch1_c0z1  kind=...    head=(无)   -> ch1_c0z1 (legacy)     ← 混合键空间
```

先遇到 `ch2_a200` 还是先遇到 `ch3_a8z0`,`Ada.json` 都来自 `ch3_a8z0.json`。

#### 「一个角色多个 kind」那一整套机制被取代了

`aliases` / `find_kin` / 「创建独立预设」/「尝试匹配同角色配置」原本就是为
"同一个人有多个 kind_id"造的。已识别角色不再有这个问题 —— 归并是**推导出来的**,
不再需要声明,也没有平票靠 `known` 排序的毛病。那套机制仍然为**身份未知**的目标服务
(敌人、杂项 NPC),所以不能删。

#### 角色名只翻译显示层

**canonical 名字(`Leon` / `Ada` …)同时是配置文件名**,所以它不能跟着语言变 ——
切一次语言,`Leon.json` 就找不到了。译名走 `char_<小写名>` 这组 key
(`char_leon = "里昂"`),`char_display()` 查不到就退回 canonical,
绝不把 `char_leon` 这种键名露给用户。和 `slot_label()` 一个套路。

key 用小写是为了让校验脚本认得(它只扫 `^%s+[a-z_]+ =`)。

#### 混合键空间是躲不掉的

`global_config.known` 里现在同时有角色名(`Leon`)和 kind 代号(`ch1_c0z1`)。
不在 head 表里的角色只能继续按 kind 存,这没问题 —— 下游只把键当不透明字符串用
(文件路径、内存缓存、命名存档、备份)。

#### 键解析要缓存

判"文件存不存在"要 `json.load_file`,每帧每目标探一遍太贵。缓存住,
只在写配置(`save_config`)和迁移之后失效 —— 那才是文件集合可能变的时刻。

### 轴的优先级:两种顺序,别混用(v0.4.0)

| 函数 | 语义 |
|---|---|
| `get_axis_names` | **优先级**顺序,靠前的优先(和层内 preset 的 `order` 一致) |
| `axis_apply_order` | **应用**顺序,和优先级**相反** |

为什么相反:`resolve` 里是后写覆盖先写,所以"优先"等于"最后写"。

#### 修掉的 bug:数字前缀的优先级原来是反的

用户用名字前缀 `0 - ` / `1 - ` / `2 - ` 表达优先级,**数字越小越优先**。
但原来的实现是按字母序应用,于是 `0 - Nake` 排最前 ⇒ 最先被写 ⇒ 被后面所有轴覆盖 ⇒
**实际优先级恰好最低**。

这个 bug 一直是**潜伏**的:实测 30 处材质重叠,但所有 body/armor 轴都只写 `false`
(`true` 计数全为 0),而 false 盖 false 是幂等的。hair 那几个轴确实写 `true`,
但它们互不重叠。所以在"只隐藏、不显示"的用法下永远看不出来 ——
一旦某个部位轴加了「显示」状态,立刻发作。

#### 高级状态组整体优先于基础状态组

有规则(条件驱动)的轴 = 面板上的「高级状态组」,**整档排在基础档之后应用**,
所以整体优先。掉血爆衣这类反应式状态应该盖掉手动摆的造型,而不是被它盖掉。

分档判据(`axis_is_advanced` = 有没有规则)**和 UI 分栏共用同一个函数** ——
否则"面板把它放在哪一栏"和"它的优先级归哪一档"可能不一致,那种错最难看出来。
注意判据是"有没有规则"而不是 `auto` —— 关掉自动的轴在面板上仍然显示在高级栏,
两边保持一致。

#### `axis_order`:可以不存在

`config.axis_order` 是显式的优先级列表。**没有这个字段时退回字母序** ——
用户的数字前缀本身就是排好的,所以旧配置不填也是对的。
`reconcile_axis_order` 和 preset 的 `reconcile_order` 同一个思路:补进来的新轴排在
**末尾**(优先级最低),新建的状态组突然压过所有已有的会很意外。

### 逐槛位闸门:一个坏槛位不该否掉整份预设(v0.4.0)

原来 `is_base_preset_usable` 返回一个布尔:整份整套造型预设要么全铺、要么全跳过。
**这一个设计踩了三次同一个坑**,每次都当成独立 bug 修:

1. v0.3.7「穿上护甲之后所有整套造型都被判不匹配」→ 当时的修法是给
   `preset_match_ratio` 加"一边空就整槛跳过"
2. v0.4.0 把雕像的 `Jacket` 映射成 `armor` → 两边非空但完全不相交,聚合从 0.87 掉到
   0.581,整个雕像不受管
3. v0.4.0 `Figure10_010` → `body` 是没被 mod 替换的 `cha004_00_TU1`,
   材质名零交集,把完好的 head/hair 一起拖下水

三个都是同一句话:**聚合成一个标量之后,最差的那个槛位决定了所有槛位的命运。**

改成逐槛位(`Utils.preset_slot_ratios` + `TransformManager.usable_slots`)之后
三个一起消失。实测 `Figure10_010`:

| 槛位 | 比值 | 旧(聚合 0.292) | 新 |
|---|---|---|---|
| body | 0.000 | 跳过 | 跳过 |
| head | 0.909 | **跳过** | 生效 |
| hair | 0.692 | **跳过** | 生效 |

#### 阈值必须跟着换,不是沿用 0.5

改成逐槛位之后先沿用了 0.5,拿实测数据一算发现它**误杀**了原来靠聚合托着的槛位:
玩家 `Default` 预设的 head 是 0.417(存的是 11 材质版、活体只有 6 个),
聚合 0.706 时整份生效,逐槛位用 0.5 就把 head 切掉了 —— 净回退。

逐槛位的实测分布(同一 mod,玩家/傀儡/雕像三类):

- 真正对不上的槛位:**0.000**
- 应该生效的槛位:**0.417 … 1.000**

中间空得很大。取 **0.25**:是"通用材质名偶然撞上"量级(≈0.08)的三倍,
又只有真实下界的 0.6 倍。换阈值后复核:玩家/傀儡**零回退**,雕像三个预设的
head+hair 全部由"不生效"变"生效",而 body 和当年那个 Jacket 仍然被正确跳过。

数据只来自一套 mod,这个数字是**可疑的**;要动就对着上面那两簇看。

#### 全启用底层刻意没跟着改

`Utils.all_enabled_preset` 那一层仍然**对所有槛位无条件铺开**。它保证的是
"没被预设点名的材质有确定值"(否则会留下游戏当时的残留状态),
和"预设在这个槛位上可不可用"是两个问题;而且预设整份不可用时(含选了「(无)」)
全启用本来就是既定的兜底行为。只把**预设的覆盖**改成逐槛位,改动面最小。

#### 变化签名要带上生效的槛位集合

`sig` 里不能只记"选了哪个预设"。穿脱护甲会让 `usable` 集合变化而 `base_name` 不变,
只记名字的话 `changed` 恒为假,那一次变化永远不会被重写。

#### UI 变成三态

`[材质不匹配,已跳过]` 现在只在**一个槛位都对不上**时出现;部分对不上显示
`[以下槛位不匹配,已跳过: 身体]`。只报"模型上真有、预设里也写了、但对不上"的槛位 ——
模型上不存在的槛位(没穿护甲时的 armor)不是问题,报出来是噪音。

### `find_kin` 必须遍历全部预设取最高分(踩过)

原来只看 `pairs()` 撞见的第一个预设就 `break`,理由是"整份快照,材质集一致就够"。
**错的**:预设可能是空的(旧版本 `normalize` 会把缺失槛位补成 `{materials = {}}`)
或者很旧,于是匹配会**随哈希顺序随机失败**。

### 「尝试匹配同角色配置」只在配置没什么可丢时出现

建立共用会让本角色自己那份配置文件被旁路掉(别名指向别处),里面的预设就成了孤儿。
所以按钮只在 `config_is_trivial()` 为真时显示:没有状态组,且整套造型预设最多只有一个
自动生成的 `default`。

### 已知角色登记表

`GlobalSettings.json` 的 `known` 数组。因为 json API **没有目录枚举**,"有哪些角色配置存在"
必须自己记。登记放在 `on_frame`(玩到就登记)而不是只放 UI 里 —— 否则没打开过面板的角色
永远不会成为认亲候选。`load_global_settings` 早期只读 `language`,漏读 `known` 会让登记表
每次重载都清空(已修)。
